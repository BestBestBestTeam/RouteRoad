# RouteRoad Backend

Java Backend системы диспетчеризации встреч по доставке банковских карт.
Он отвечает за бизнес-данные и REST API заявок, представителей и офисов,
а также за проверку и активацию рассчитанных планов. Сейчас реализован
каркас приложения и проверочный endpoint; бизнес-функциональность появится позже.

Стек: Java 25 LTS, Spring Boot 4.1.2, Maven 3.10.0 (через Maven Wrapper),
Spring WebMVC, Spring Data JPA с Hibernate ORM, PostgreSQL JDBC Driver,
Jakarta Bean Validation и Flyway.

Минимальный Spring Boot-проект. Требуется JDK 25 LTS; `JAVA_HOME` должен указывать на него.
Maven скачивается автоматически через Maven Wrapper при первом запуске
(необходим доступ к Maven Central).

Команды из корня репозитория:

```sh
cd backend
./mvnw clean verify
./mvnw spring-boot:run
```

В Windows используйте `mvnw.cmd` вместо `./mvnw`.

Приложение запускается на порту `8080`. Проверочный endpoint доступен
по `/api/health`; корневой путь `/` по-прежнему возвращает `404`.

Исполняемый JAR после сборки:

```sh
java -jar target/routeroad-backend-0.0.1-SNAPSHOT.jar
```

Подключены Spring Data JPA (Hibernate ORM приходит через starter), PostgreSQL JDBC,
Validation и Flyway. Для Spring Boot 4 используется `spring-boot-starter-flyway`:
он подключает `flyway-core` и интеграцию со Spring Boot. Поддержка PostgreSQL
подключена через `flyway-database-postgresql`. Версии зависимостей управляются
Spring Boot BOM; отдельные версии Hibernate, JDBC-драйвера и Flyway не заданы.

## Health endpoint

`GET /api/health` проверяет доступность HTTP-приложения:

```sh
curl -i http://localhost:8080/api/health
```

Ожидаемый ответ:

```http
HTTP/1.1 200
Content-Type: application/json

{"status":"UP"}
```

Endpoint возвращает постоянный статус `UP`. Он не обращается к PostgreSQL,
Hibernate, Flyway или Python и не проверяет их состояние. Это проверка
доступности приложения, а не готовности БД или интеграций.
Контроллер и record ответа находятся в `com.routeroad.shared.api`;
отдельные сервисы и Spring Boot Actuator для него не используются.

## Configuration and profiles

| Файл | Назначение |
| --- | --- |
| `src/main/resources/application.yml` | Имя приложения и временный режим запуска без БД. |
| `src/main/resources/application-local.yml` | Локальная PostgreSQL, Hibernate и Flyway; активируется профилем `local`. |
| `src/test/resources/application-test.yml` | Настройки будущих интеграционных тестов PostgreSQL; активируется профилем `test` на тестовом classpath и не попадает в рабочий JAR. |

Без явно активированного профиля приложение и существующий `contextLoads`
запускаются **без БД** обычными командами выше. Второй документ `application.yml`
временно исключает `DataSourceAutoConfiguration` только при условии
`!local & !test`. Без `DataSource` не активируются зависимые настройки JPA и Flyway.
При активном `local` или `test` этот документ не загружается вообще: исключение
не нужно переопределять пустым списком. Одновременно активировать `local` и
`test` для обычной разработки не следует.

Временный режим действует также для других профилей, кроме `local` и `test`.
До появления остальных окружений и настройки PostgreSQL этот режим нужен
только для проверки каркаса приложения и не предназначен для эксплуатации.

Для `local` нужно задать в окружении процесса или в Run Configuration IDEA:

| Переменная | Значение |
| --- | --- |
| `DB_URL` | JDBC URL PostgreSQL в формате `jdbc:postgresql://<host>:<port>/<database>`. |
| `DB_USERNAME` | Имя пользователя БД. |
| `DB_PASSWORD` | Пароль пользователя БД. |

Значения по умолчанию не заданы. Реальные пароли и URL с секретами нельзя
записывать в YAML, README или коммитить. Spring Boot не читает `.env` сам:
переменные должны быть переданы запускаемому процессу.

### Local environment file

`backend/.env.example` — общий шаблон переменных для локальной PostgreSQL.
Он хранится в Git и содержит только пример подключения и пароль-заглушку
`change_me`. Из каталога `backend` создайте свою копию:

```sh
cp .env.example .env
```

В `.env` замените URL, имя пользователя и пароль значениями своей локальной БД.
Файлы `.env`, `.env.local` и другие `.env.*`, включая `.env.*.local`,
игнорируются Git; `.env.example` остаётся доступным для коммита.
Настоящие пароли нельзя коммитить: репозиторий и его история доступны команде,
а удаление пароля следующим коммитом не убирает его из истории.

Spring Boot **не загружает `.env` автоматически**. Для macOS/Linux можно
передать переменные через оболочку (команды из каталога `backend`):

```sh
(
  set -a
  . ./.env
  set +a
  ./mvnw spring-boot:run -Dspring-boot.run.profiles=local
)
```

Этот вариант выполняет локальный `.env` как файл оболочки. Используйте свой
доверенный файл с синтаксисом `NAME=value`; значения с пробелами и специальными
символами заключайте в одинарные кавычки. Подоболочка ограничивает действие
переменных этим запуском. Сам файл `.env.example` не создаёт БД и пользователя.

В IntelliJ IDEA откройте **Run → Edit Configurations**, выберите запуск
`RouteRoadApplication` и в **Environment variables** задайте `DB_URL`,
`DB_USERNAME`, `DB_PASSWORD`. В **Program arguments** укажите
`--spring.profiles.active=local`. Наличие `.env` рядом с проектом само по себе
не передаёт значения в IDEA; при этом способе внесите их в окружение запуска.
Не публикуйте конфигурации запуска с настоящими секретами.

Активация `local` из каталога `backend`:

```sh
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
```

Либо через окружение:

```sh
SPRING_PROFILES_ACTIVE=local ./mvnw spring-boot:run
```

Или для собранного JAR:

```sh
java -jar target/routeroad-backend-0.0.1-SNAPSHOT.jar --spring.profiles.active=local
```

В IDEA профиль можно задать переменной `SPRING_PROFILES_ACTIVE=local`
или аргументом программы `--spring.profiles.active=local`.
Для запуска без БД не задавайте `SPRING_PROFILES_ACTIVE` и профиль в аргументах.

Профили `local` и `test` используют `ddl-auto: validate`, `open-in-view: false`
и включённый Flyway. Hibernate только проверяет схему; менять её в дальнейшем
будут миграции Flyway. Сейчас миграций и PostgreSQL нет, поэтому полноценный
запуск `local` без доступной и настроенной БД не ожидается.

Интеграционные тесты отложены на неопределённый срок; существующая заготовка
профиля `test` сохранена. Профиль пока не содержит URL, пользователя и пароля.
Когда работа над интеграционными тестами возобновится, Testcontainers сможет
предоставить параметры подключения
`spring.datasource.url`, `spring.datasource.username`, `spring.datasource.password`
(например, через `@DynamicPropertySource`), а тесты явно активируют `test`.
Пока не добавлены ни Testcontainers, ни контейнерные тесты, ни H2.
Активация `test` без предоставленного подключения не должна скрывать отсутствие
БД; существующий тест контекста намеренно не активирует этот профиль.

При подключении PostgreSQL нужно удалить временный второй YAML-документ
с `spring.config.activate.on-profile` и `spring.autoconfigure.exclude`, добавить
миграции и настроить соответствующее окружение. Затем потребуется перевести
проверку полного контекста на подготовленную тестовую БД. После удаления
временного режима тест `defaultConfigurationAllowsBootstrapWithoutDatabase`
также нужно удалить или заменить проверкой новой конфигурации.

`ConfigurationProfilesTests` проверяет загрузку конфигурации и отсутствие
утечки исключения в `local`/`test`, не создавая подключений к БД.

Сущности, репозитории и миграции пока не созданы. Подключение БД выполняется
на следующих этапах. В дальнейшем схема общей БД должна управляться
миграциями Flyway.

## Architecture

Backend организуется по принципу **package-by-feature**: классы группируются
по функциональным модулям, а внутри модуля — по ответственности. Это пакеты
одного Maven-приложения, а не отдельные Maven-модули или микросервисы.

Ниже зафиксирована целевая структура. Сейчас реализованы точка входа
`com.routeroad.RouteRoadApplication`, `HealthController` и `HealthResponse`
в `com.routeroad.shared.api`,
а также существующие тесты `RouteRoadApplicationTests` и `ConfigurationProfilesTests`.
Функциональные пакеты
создаются по мере появления реального кода: пустые каталоги, `.gitkeep`,
классы-заглушки и интерфейсы только ради структуры не нужны.

```text
backend/
├── pom.xml
├── mvnw / mvnw.cmd
├── .mvn/wrapper/maven-wrapper.properties
└── src/
    ├── main/
    │   ├── java/com/routeroad/
    │   │   ├── RouteRoadApplication.java
    │   │   ├── orders/
    │   │   │   ├── api/
    │   │   │   ├── application/
    │   │   │   ├── domain/
    │   │   │   └── infrastructure/
    │   │   ├── couriers/
    │   │   │   ├── api/
    │   │   │   ├── application/
    │   │   │   ├── domain/
    │   │   │   └── infrastructure/
    │   │   ├── offices/
    │   │   │   ├── api/
    │   │   │   ├── application/
    │   │   │   ├── domain/
    │   │   │   └── infrastructure/
    │   │   ├── planning/
    │   │   │   ├── api/
    │   │   │   ├── application/
    │   │   │   ├── domain/
    │   │   │   └── infrastructure/
    │   │   ├── execution/
    │   │   │   ├── api/
    │   │   │   ├── application/
    │   │   │   ├── domain/
    │   │   │   └── infrastructure/
    │   │   ├── simulation/
    │   │   │   ├── api/

        └── resources/application-test.yml
```

Ответственность модулей:

| Пакет | Ответственность |
| --- | --- |
| `orders` | Заявки на доставку карт, их жизненный цикл и правила изменения данных заявки. |
| `couriers` | Представители, их доступность, смены и текущие координаты. |
| `offices` | Банковские офисы и их параметры, необходимые для диспетчеризации. |
| `planning` | Маршруты, точки маршрутов и назначения; взаимодействие с Python, проверка и активация результатов планирования. |
| `execution` | Фактические статусы встреч, события исполнения и использование активированного плана. Изменения данных заявки выполняются через контракт `orders.application`. |
| `simulation` | Модельное время, управление сценариями симуляции и взаимодействие с симулятором. |
| `shared` | Общие технические настройки (`config`), обработка ошибок (`error`) и проверочный HTTP endpoint (`api`). |

Пакет не создаётся автоматически для каждой таблицы. Например, будущие
`route`, `route_stop` и `assignment` относятся к `planning`. Таблицы запусков
планирования, смен и симуляции будут распределяться по смыслу: `planning`,
`couriers` и `simulation` соответственно. Схема и названия таблиц на этом шаге
не утверждаются.

Правила размещения классов и зависимостей:

| Слой | Что размещать | Допустимые зависимости |
| --- | --- | --- |
| `api` | REST-контроллеры, DTO запросов и ответов, преобразование HTTP-данных. | Публичные сценарии собственного `application`; без прямого доступа к репозиториям и `infrastructure`. |
| `application` | Сценарии использования, координация операций и транзакционные границы; при необходимости контракты доступа к хранилищам и внешним системам. | Собственный `domain`, контракты своего модуля и явно опубликованные контракты `application` других модулей. |
| `domain` | Бизнес-модели, правила, ограничения и бизнес-исключения; при необходимости доменные контракты. | Без зависимостей от `api`, `infrastructure`, HTTP, JPA и внутренних классов других модулей. |
| `infrastructure` | JPA-модели хранения, Spring Data репозитории, реализации контрактов доступа к БД, адаптеры Python и других внешних систем. | Контракты собственного `application`/`domain` и технические библиотеки. |

- Контроллер вызывает сценарий `application`, который применяет правила
  `domain`. Доступ к БД или внешнему сервису выполняется через контракт,
  реализованный в `infrastructure`. Интерфейсы и отдельные модели вводятся
  только при функциональной необходимости.
- `application` и `domain` не импортируют реализации из `infrastructure`.
  Реализация подключается через внедрение зависимостей Spring.
- Межмодульные вызовы проходят через явно опубликованные контракты
  `application`: публичные сценарии и предназначенные для них типы данных.
  HTTP DTO, JPA-сущности и Spring Data репозитории не являются такими контрактами.
  Внутренние классы чужих `domain` и `infrastructure` напрямую не используются.
- Циклические зависимости между функциональными модулями не допускаются.
  Если появляется цикл, нужно пересмотреть ответственность сценария или контракт;
  перенос бизнес-логики в `shared` не является решением.
- Общая техническая конфигурация может находиться в `shared.config`, обработка
  ошибок — в `shared.error`, технический health endpoint — в `shared.api`.
  Для health endpoint без бизнес-логики отдельный слой `application` не нужен.
  Специфичная для модуля конфигурация остаётся в его
  `infrastructure`, а бизнес-правила и бизнес-исключения — в его `domain`.
  `shared` не зависит от функциональных модулей и не содержит их сервисов,
  репозиториев или бизнес-моделей.
- `planning` отвечает за принятие результата расчёта, а `execution` — за
  исполнение принятого плана. Наличие строк, записанных Python, само по себе
  не означает активацию плана. Java проверяет и активирует результат через
  сценарии `planning.application`.
- Python напрямую читает общую PostgreSQL и записывает результаты в выделенные
  таблицы. Java не пересылает ему весь набор данных. Общая схема в дальнейшем
  меняется через согласованные миграции Flyway; автоматическое создание или
  обновление схемы Hibernate не должно подменять миграции.
- Тесты функциональности размещаются в `src/test/java/com/routeroad/<feature>/`
  с тем же разделением на слои по мере необходимости.
- `RouteRoadApplication` остаётся в корневом пакете `com.routeroad`, чтобы
  стандартное сканирование компонентов охватывало функциональные подпакеты.

На этом этапе правила зафиксированы документацией. Автоматические проверки
архитектурных зависимостей и дополнительные библиотеки не подключены.
