## Контракт

### Принципы
- Java владеет схемой БД и основными данными, ведёт модельное время, синхронизацию и разрешение конфликтов. Python считает и пишет в БД только таблицы плана.
- Python читает общую БД напрямую. Миграции схемы ведёт Java.
- Формат: JSON, `snake_case`, время ISO 8601 с зоной (`2026-10-20T09:30:00+03:00`), идентификаторы UUID, координаты `lat`/`lon` (WGS84), расстояния в метрах, длительности в секундах.
- Представитель работает по всему городу и привязан к своему офису.

### Таблицы

Читают все, пишет один. Типы предварительные.

**`service_order` — заявка (встреча с клиентом), пишет Java**

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | UUID | Идентификатор заявки |
| `client_name` | строка | Имя клиента |
| `lat`, `lon` | число | Координаты места встречи |
| `window_from` | время | Начало временного окна, в которое должна начаться встреча |
| `window_to` | время | Конец временного окна |
| `service_duration_s` | целое | Сколько секунд длится встреча |
| `status` | перечисление | Текущее состояние |
| `service_date` | дата | День, на который назначена заявка. При переносе сдвигается на день вперёд, статус возвращается в `NEW` |
| `version` | целое | Номер версии, растёт при каждом изменении. Нужен для конфликтов синхронизации |

**`courier` — представитель, пишет Java**

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | UUID | Идентификатор представителя |
| `name` | строка | Имя представителя |
| `office_id` | UUID | Свой офис: откуда начинает день и куда едет за новыми картами |
| `shift_start` | время | Начало рабочей смены |
| `shift_end` | время | Конец смены, за неё маршрут выходить не может |
| `position` (`lat`, `lon`, `at`) | число, число, время | Последняя известная позиция и время её получения |
| `is_available` | да/нет | `false`, если представитель отказался от работы на сегодня (`COURIER_REFUSED`) или снят диспетчером. Нахождение на смене сюда не входит |

**`office` — офис, пишет Java**

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | UUID | Идентификатор офиса |
| `name` | строка | Название |
| `lat`, `lon` | число | Координаты. Начало дня и место получения карт |

В MVP одна запись, схема рассчитана на несколько.

**`planning_run`: запуск расчёта, пишет Python**

| Поле | Тип | Описание |
| --- | --- | --- |
| `plan_version` | целое | Глобальный номер запуска (sequence). Первичный ключ |
| `request_id` | UUID | Идентификатор запроса. Уникален: при повторе того же запроса возвращается прежний результат, новый план не создаётся |
| `run_type` | перечисление | `ASSIGN` или `REASSIGN` |
| `event_type` | перечисление | Тип события для `REASSIGN` (`COURIER_REFUSED` и т.д.), иначе пусто |
| `algorithm` | перечисление | `greedy` или `ortools` |
| `plan_date` | дата | День, который считали |
| `model_now` | время | Модельное время запроса (`now`) |
| `created_at` | время | Когда запись создана (модельное время) |

Каждый запуск `/assign` и `/reassign` создаёт ровно одну запись. Маршруты и назначения этого запуска ссылаются на неё через `plan_version`.

**`route` — маршрут представителя на день, пишет Python кроме `is_active`**

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | UUID | Идентификатор маршрута |
| `courier_id` | UUID | Чей маршрут |
| `plan_date` | дата | На какой день |
| `plan_version` | целое | Ссылка на `planning_run`. Версия запуска, в котором маршрут создан |
| `is_active` | да/нет | **Пишет Java.** Python создаёт маршрут с `false`. После проверки Java делает его активным |
| `algorithm` | перечисление | Каким алгоритмом построен (`greedy` или `ortools`) |
| `total_distance_m` | целое | Суммарное расстояние маршрута |
| `violated_windows` | целое | Сколько временных окон нарушено |
| `created_at` | время | Когда построен |

Не больше одного активного маршрута на `(courier_id, plan_date)`: частичный уникальный индекс `WHERE is_active`.

При частичном `/reassign` новые маршруты создаются только у изменённых представителей. У остальных остаются прежние активные маршруты со своей старой `plan_version`. Поэтому «актуальный план дня» это все маршруты с `is_active = true`, а не маршруты с максимальной версией.

**`route_stop` — точка маршрута, пишет Python**

| Поле | Тип | Описание |
| --- | --- | --- |
| `route_id` | UUID | К какому маршруту относится |
| `sequence` | целое | Порядковый номер точки в маршруте |
| `type` | перечисление | `OFFICE` (офис, в том числе заезд за картами) или `ORDER` (клиент) |
| `order_id` | UUID | Заявка, если `type = ORDER`, иначе пусто |
| `office_id` | UUID | Офис, если `type = OFFICE`, иначе пусто |
| `arrival_eta` | время | Ожидаемое прибытие |
| `departure_eta` | время | Ожидаемый отъезд |
| `distance_from_prev_m` | целое | Расстояние от предыдущей точки |
| `window_violation_s` | целое | На сколько секунд нарушено временное окно (0, если не нарушено) |

Порядок и время хранятся только здесь. Первая точка маршрута — офис.

**`assignment` — решение по заявке, пишет Python**

| Поле | Тип | Описание |
| --- | --- | --- |
| `order_id` | UUID | Заявка |
| `courier_id` | UUID | Кому назначена. Пусто, если назначить не удалось |
| `route_id` | UUID | Маршрут, в который попала заявка |
| `plan_version` | целое | Запуск, в рамках которого принято решение |
| `source_order_version` | целое | Значение `service_order.version`, по которому считали. Нужно для проверки конфликтов при активации |
| `reason_code` | перечисление | Код причины |
| `reason_text` | строка | Причина простыми словами для диспетчера |
| `decided_by` | перечисление | `SYSTEM` (алгоритм, в том числе авто после таймаута) или `DISPATCHER` (ручное переназначение) |
| `created_at` | время | Когда принято решение (модельное время) |

Старые записи не удаляются: это журнал назначений.

### Статусы
- **Статусы встречи (в мобильном приложении ровно шесть):** `EN_ROUTE` — «В пути», `ARRIVED` — «Прибыл», `IN_PROGRESS` — «Встреча начата», `COMPLETED` — «Завершена успешно», `RESCHEDULED` — «Перенесена», `CANCELLED` — «Отменена».
- **Состояния до начала встречи:** `NEW` (создана), `ASSIGNED` (стоит в активном маршруте), `UNASSIGNED` (назначить не удалось).

### Коды причин (`reason_code`)

| Код | Смысл |
| --- | --- |
| `NEAREST` | Ближайший подходящий представитель |
| `FREE_WINDOW` | Есть свободное время в маршруте, окно заявки соблюдается |
| `OPTIMIZED` | Решение оптимизатора (OR-Tools) |
| `REASSIGNED_AFTER_REFUSAL` | Перераспределена после отказа представителя |
| `MANUAL_DISPATCHER` | Ручное переназначение диспетчером (Java вызывает `/reassign`, запись делает Python) |
| `AUTO_AFTER_TIMEOUT` | Автоматическое перераспределение после 10 минут без решения диспетчера |
| `NO_CAPACITY` | Нет времени в сменах (неназначенная заявка) |
| `WINDOW_INFEASIBLE` | Временное окно невыполнимо (неназначенная заявка) |
| `DEFER_NEXT_DAY` | Перенос на следующий день (неназначенная заявка) |

### Запросы расчёта (Python)

**`POST /assign` — назначение и построение маршрутов.** Python сам читает состояние из БД, считает и записывает план.

| Поле запроса | Описание |
| --- | --- |
| `request_id` | Идентификатор запроса |
| `now` | Текущее модельное время |
| `algorithm` | `greedy` или `ortools` |
| `scope.date` | День, который считаем |
| `config.speed_kmh` | Скорость для пересчёта расстояния во времени |
| `config.window_mode` | Режим временных окон (`soft` — нарушение допустимо со штрафом) |

| Поле ответа | Описание |
| --- | --- |
| `request_id` | Эхо запроса |
| `plan_version` | Версия записанного плана |
| `routes_written`, `assignments_written` | Сколько маршрутов и назначений записано |
| `unassigned` | Список не назначенных заявок: `order_id`, `reason_code`, `reason_text` |
| `metrics` | `total_distance_m`, `violated_windows`, `unassigned_count`, `solve_time_ms` |

**`POST /reassign` — перераспределение при событии.** Запрос: `request_id`, `now`, `algorithm` и `event`. Python читает текущие маршруты из БД, пересчитывает затронутые и записывает только изменения. Ответ: `request_id`, `plan_version`, `changed_couriers`, `assignments_written`, `unassigned`, `metrics`.

| `event.type` | Что делает расчёт |
| --- | --- |
| `CLIENT_CANCELLED` | Заявка убирается без перераспределения, маршрут перестраивается только у этого представителя |
| `COURIER_REFUSED` | Заявки представителя распределяются между свободными в конце их смены, не влезшие переносятся на следующий день. Может добавиться заезд в офис за картами |
| `COURIER_DELAYED` | Обновляет ETA и проверяет окна, при нарушении алерт создаёт Java |
| `AUTO_REASSIGN_REQUEST` | Диспетчер нажал «перераспределить автоматически» или истёк 10-минутный срок |
| `MANUAL_REASSIGN` | Диспетчер выбрал представителя: в событии `order_id` и `target_courier_id`, расчёт ставит заявку в его маршрут |

Поля `event`: `type`, `courier_id`, `order_ids` (и `target_courier_id` для `MANUAL_REASSIGN`).

### Правила записи плана

1. Python пишет `planning_run`, `route` (с `is_active = false`), `route_stop` и `assignment` одной транзакцией.
2. Перед записью Python сверяет `version` заявок, по которым считал. Если Java успела их изменить, ничего не записывается, ответ `CONFLICT` (409), запрос можно повторить.
3. Блокировать строки заявок Python не может (у него только `SELECT` на них), поэтому окончательная проверка делается на стороне Java при активации: Java сверяет `assignment.source_order_version` с текущей `service_order.version`. Если не совпало, план не активируется, Java запрашивает пересчёт.
4. После записи Python вызывает `POST /plans/ready` с `plan_version`. Java проверяет план и в одной транзакции выключает старые маршруты затронутых представителей и включает новые (`is_active`).
5. Java после активации обновляет панель диспетчера, рассылает маршруты, создаёт алерты.
6. Python при расчёте читает только активные маршруты. Неактивированный план на расчёт не влияет.
7. Повторный запрос с тем же `request_id` возвращает результат первого запуска, дубликаты не создаются.
8. Права Python в БД: `SELECT` на всё, `INSERT` на `planning_run`, `route`, `route_stop`, `assignment`. `UPDATE` не нужен.


### Симулятор и Java
Симулятор работает как клиент Java через те же операции, что и PWA. Сценарий создаёт генератор Python (по конфигу и `seed`), в БД он попадает обычными записями.

| Операция | Эндпоинт | Кто вызывает |
| --- | --- | --- |
| Задать модельное время | `PUT /sim/clock` (`now`, `speed`) | Симулятор |
| Загрузить сценарий | `POST /sim/scenario` (`seed`, `config`, `offices`, `couriers`, `orders`) | Симулятор |
| Очистить данные перед новым сценарием | `POST /sim/reset` | Симулятор |
| Сменить статус встречи | `POST /orders/{id}/status` (`status`, `courier_id`, `occurred_at`, `base_version`) + `Idempotency-Key` | PWA, симулятор |
| Отправить позицию | `POST /couriers/{id}/position` (`lat`, `lon`, `at`) | PWA, симулятор |
| Событие «отмена клиентом», «отказ», «задержка» | `POST /events` (`type`, поля события) | Симулятор |
| Передать накопленные офлайн-действия | `POST /sync` (пачка действий) | PWA, симулятор |
| Получить маршрут представителя | `GET /couriers/{id}/schedule` | PWA, симулятор |

Офлайн-действие в пачке: `client_action_id`, `order_id`, `status`, `occurred_at`, `base_version`. Ответ Java по каждому: `APPLIED`, `DUPLICATE` (уже принято) или `CONFLICT` с причиной и актуальным состоянием заявки.

**Конфликты.** Диспетчер переназначает заявку только после алерта, дедлайн 10 минут модельного времени, затем автоматическое перераспределение. Если `base_version` совпадает, действие применяется. Если нет, побеждает действие, совершённое раньше. Если курьер уже отметил `IN_PROGRESS` или `COMPLETED`, встреча остаётся за ним, переназначение отклоняется, диспетчер получает алерт.

### Ошибки
Единый формат: `{ "error": { "code", "message", "details" } }`. Коды: `VALIDATION_ERROR` (400), `NOT_FOUND` (404), `CONFLICT` (409), `INFEASIBLE` (422, план построить нельзя), `INTERNAL_ERROR` (500).
