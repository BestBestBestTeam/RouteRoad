# Внутренний контракт Java/Python

Справочная основа расчётного ядра из контракта, переданного пользователем.
Полный обновлённый состав сущностей, их расширения и все HTTP-ручки находятся
в [frontend-api.md](frontend-api.md). Для реализации текущей задачи использовать
этот единый документ; он учитывает оба отказа и общий API PWA/симулятора.

## Принципы

- Java владеет схемой БД и основными данными, ведёт модельное время, синхронизацию
  и разрешение конфликтов. Миграции схемы ведёт Java.
- Python читает общую БД напрямую, считает и пишет только таблицы плана.
- JSON: `snake_case`; время — ISO 8601 с зоной, например
  `2026-10-20T09:30:00+03:00`; идентификаторы — UUID; координаты — `lat`/`lon`
  (WGS84); расстояния — метры; длительности — секунды.
- Представитель работает по всему городу и привязан к своему офису.

| Поле           | Тип          | Описание                                                                               |
| -------------- | ------------ | -------------------------------------------------------------------------------------- |

| `run_type`     | перечисление | `ASSIGN` или `REASSIGN`                                                                |

### `route` — маршрут представителя на день

Пишет Python, кроме `is_active`, которое меняет Java.

| Поле               | Тип          | Описание                                                       |
| ------------------ | ------------ | -------------------------------------------------------------- |
| `id`               | UUID         | Идентификатор маршрута                                         |
| `courier_id`       | UUID         | Представитель                                                  |
| `plan_date`        | дата         | День маршрута                                                  |
| `plan_version`     | целое        | Ссылка на `planning_run`, в котором маршрут создан             |
| `is_active`        | да/нет       | Python создаёт `false`; после проверки Java активирует маршрут |
| `algorithm`        | перечисление | `greedy` или `ortools`                                         |
| `total_distance_m` | целое        | Суммарное расстояние маршрута                                  |
| `violated_windows` | целое        | Количество нарушенных временных окон                           |
| `created_at`       | время        | Время построения                                               |

Не больше одного активного маршрута на `(courier_id, plan_date)`:

При частичном `/reassign` новые маршруты создаются только у изменённых
представителей. У остальных сохраняются прежние активные маршруты со своей
`plan_version`. Актуальный план дня — **все маршруты с `is_active = true`**,
а не маршруты с максимальной версией.

## Статусы

В мобильном приложении шесть статусов встречи:
`EN_ROUTE`, `ARRIVED`, `IN_PROGRESS`, `COMPLETED`, `RESCHEDULED`, `CANCELLED`
(«В пути», «Прибыл», «Встреча начата», «Завершена успешно», «Перенесена», «Отменена»).

До начала встречи: `NEW` (создана), `ASSIGNED` (в активном маршруте),
`UNASSIGNED` (назначить не удалось).

## Коды причин назначения

| `reason_code`              | Смысл                                                                  |
| -------------------------- | ---------------------------------------------------------------------- |
| `NEAREST`                  | Ближайший подходящий представитель                                     |
| `FREE_WINDOW`              | Свободное время в маршруте с соблюдением окна                          |
| `OPTIMIZED`                | Решение OR-Tools                                                       |
| `REASSIGNED_AFTER_REFUSAL` | Перераспределение после отказа представителя                           |
| `MANUAL_DISPATCHER`        | Ручное переназначение; Java вызывает `/reassign`, запись делает Python |
| `AUTO_AFTER_TIMEOUT`       | Автоматическое перераспределение после 10 минут без решения            |
| `NO_CAPACITY`              | Нет времени в сменах, заявка не назначена                              |
| `WINDOW_INFEASIBLE`        | Окно невыполнимо, заявка не назначена                                  |
| `DEFER_NEXT_DAY`           | Перенос на следующий день, заявка не назначена                         |

## Расчёт: внутренний API Python

### `POST /assign`

Python читает БД, считает и записывает план.

| Запрос               | Содержание                                        |
| -------------------- | ------------------------------------------------- |
| `request_id`         | Идентификатор запроса                             |
| `now`                | Текущее модельное время                           |
| `algorithm`          | `greedy` или `ortools`                            |
| `scope.date`         | Рассчитываемый день                               |
| `config.speed_kmh`   | Скорость для пересчёта расстояния во время        |
| `config.window_mode` | Режим окон; `soft` допускает нарушение со штрафом |

Ответ: `request_id`, `plan_version`, `routes_written`, `assignments_written`,
`unassigned` (элементы `order_id`, `reason_code`, `reason_text`),
`metrics` (`total_distance_m`, `violated_windows`, `unassigned_count`, `solve_time_ms`).

### `POST /reassign`

Запрос: `request_id`, `now`, `algorithm`, `event`. Python читает текущие
активные маршруты и записывает только изменения.

Ответ: `request_id`, `plan_version`, `changed_couriers`, `assignments_written`,
`unassigned`, `metrics`.

| `event.type`            | Действие                                                                                                        |
| ----------------------- | --------------------------------------------------------------------------------------------------------------- |
| `CLIENT_CANCELLED`      | Убрать заявку, перестроить маршрут только её представителя                                                      |
| `ORDER_REFUSED`         | Переназначить одну отказанную заявку, исключив отказавшегося представителя; остальные его заявки не затрагивать |
| `COURIER_REFUSED`       | Распределить заявки между свободными в конце смен; не вместившиеся перенести на завтра; возможен заезд в офис   |
| `COURIER_DELAYED`       | Обновить ETA и проверить окна; алерт при нарушении создаёт Java                                                 |
| `AUTO_REASSIGN_REQUEST` | Автоматическое перераспределение по кнопке диспетчера или по истечении 10 минут                                 |
| `MANUAL_REASSIGN`       | Поставить заявку в маршрут выбранного представителя; указаны `order_id` и `target_courier_id`                   |

Общие поля `event`: `type`, `courier_id`, `order_ids` и `target_courier_id`
для `MANUAL_REASSIGN`. Для одной заявки `order_ids` содержит один ID, в том числе
для ручного события. Отказ одной заявки — `ORDER_REFUSED`, а `COURIER_REFUSED`
сохраняет отдельный смысл полной недоступности представителя.

Java сохраняет отказ в `business_event` и повышает `service_order.version`;
Python читает исключение пары заявка/представитель из общей БД при любом расчёте.
Начатую встречу не отнимают. При ручном или автоматическом решении Java передаёт
соответствующий тип команды; причина отказа и ограничение при этом не теряются.

## Запись и активация плана

1. Python пишет `planning_run`, `route` с `is_active = false`, `route_stop`
   и `assignment` одной транзакцией.
2. Перед записью Python сверяет версии заявок. Если Java успела изменить заявки,
   Python ничего не записывает и отвечает `CONFLICT` (409); запрос можно повторить.
3. Python не может блокировать строки заявок: на них только `SELECT`.
   При активации Java окончательно сравнивает `assignment.source_order_version`
   с текущей `service_order.version`. При несовпадении не активирует план,
   запрашивает пересчёт.
4. После записи Python вызывает Java: `POST /plans/ready` с `plan_version`.
   Java проверяет план и одной транзакцией выключает старые маршруты затронутых
   представителей и включает новые.
5. После активации Java обновляет панель, рассылает маршруты, создаёт алерты.
   Неактивированный план на расчёт не влияет: Python читает только активные маршруты.
6. Повтор с тем же `request_id` возвращает результат первого запуска без дубликатов.
   Права Python: `SELECT` на всё; `INSERT` на `planning_run`, `route`,
   `route_stop`, `assignment`; `UPDATE` не нужен.

## Симулятор и Java

Симулятор выполняет действия представителя теми же Java-ручками, телами запросов,
версиями и ключами идемпотентности, что PWA. Отдельного обработчика отказа или
задержки для симулятора нет. Расчётный Python `/assign`/`/reassign` — другой контур.
Сценарий генерирует Python, Java сохраняет его в общую БД.

| Операция                 | Метод и путь, данные                                                                                           | Кто вызывает                                   |
| ------------------------ | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| Задать модельное время   | `PUT /sim/clock`: `now`, `speed`                                                                               | Симулятор                                      |
| Загрузить сценарий       | `POST /demo/scenarios`: `date`, необязательный `seed`                                                          | Диспетчер / симулятор с соответствующим правом |
| Очистить сценарий        | `POST /demo/reset`                                                                                             | Диспетчер / симулятор с соответствующим правом |
| Сменить статус           | `POST /orders/{id}/status`: `status`, `courier_id`, `occurred_at`, `base_version`; заголовок `Idempotency-Key` | PWA, симулятор                                 |
| Отправить позицию        | `POST /couriers/{id}/position`: `lat`, `lon`, `at`                                                             | PWA, симулятор                                 |
| Отказ от одной заявки    | `POST /orders/{id}/refusal`: `reason`, `occurred_at`, `base_version`; `Idempotency-Key`                        | PWA, симулятор                                 |
| Задержка                 | `POST /orders/{id}/delay`: `delay_s`, `occurred_at`, `base_version`; `Idempotency-Key`                         | PWA, симулятор                                 |
| Отмена клиентом          | `POST /events`: `type=CLIENT_CANCELLED`, поля события                                                          | Симулятор: событие внешнего клиента            |
| Передать офлайн-действия | `POST /sync`: пачка действий                                                                                   | PWA, симулятор                                 |
| Получить маршрут         | `GET /couriers/{id}/schedule`                                                                                  | PWA, симулятор                                 |

Действие в `/sync`: `client_action_id`, `order_id`, `status`, `occurred_at`,
`base_version`. Результат Java для каждого: `APPLIED`, `DUPLICATE` либо `CONFLICT`
с причиной и актуальным состоянием заявки.

`/sim/clock` управляет модельным временем и не подменяет действия PWA.
Симулятор действует от имени соответствующего представителя с теми же проверками
доступа; для подготовки сценария использует полномочия диспетчера/тестового контура.

Диспетчер переназначает только после алерта. Дедлайн — 10 минут модельного времени,
затем автоматическое перераспределение. Если `base_version` совпадает, действие
применяется; иначе побеждает совершённое раньше. Если представитель уже отметил
`IN_PROGRESS` или `COMPLETED`, встреча остаётся за ним, переназначение отклоняется,
диспетчер получает алерт.

## Ошибки

Формат: `{ "error": { "code", "message", "details" } }`.

| HTTP | `code`                               |
| ---- | ------------------------------------ |
| 400  | `VALIDATION_ERROR`                   |
| 404  | `NOT_FOUND`                          |
| 409  | `CONFLICT`                           |
| 422  | `INFEASIBLE` — план построить нельзя |
| 500  | `INTERNAL_ERROR`                     |
