# Архитектура фронтенда RouteRoad

Обновлено **9 ноября 2026 года**. Текущий этап — UI двух ролей на синтетических данных и планирование Java API. Реализованы асинхронный demo API, отдельные загрузка заявок и построение демонстрационных маршрутов, интерактивная карта. Java, настоящая авторизация, дорожный расчёт, PWA и IndexedDB пока не подключены.

Требования к интерфейсу — [vision.md](vision.md) и [decisions.md](decisions.md).
[Внутренний контракт Java/Python](entity.md) описывает их БД и расчёты, а не типы
фронтенда. Все обновлённые сущности, DTO и ручки для Java-разработчика собраны
в [frontend-api.md](frontend-api.md). HTTP пока не реализован. Визуальное направление
и исходные экраны взяты из [Figma](https://www.figma.com/design/cg5e0CP1iZShR9gogzFxsP);
изображение карты заменено Leaflet.

Источником ответа остаётся та же общая БД через Java. Python-симулятор выполняет
действия представителя теми же Java-ручками и проверками, что PWA.

## 1. Почему теперь такая структура

Пользователь выбрал организацию по образцу существующего CoonSpect: `components/pages/stores/utils/types/routes/api`. Это **layer-based / type-based** подход: сначала разделяем файлы по ответственности, затем группируем компоненты и страницы по назначению. Предыдущее `app/pages/modules/shared` заменено этим выбором. CoonSpect изучен, но не изменён; его версии пакетов и реализация авторизации не копировались.

Это не FSD и не структура Atomic Design. Atomic Design остаётся полезным принципом композиции: кнопка → карточка → список → экран; обязательных папок `atoms/molecules/organisms` нет. API, stores и маршрутизация требуют своих правил независимо от размера UI-компонента.

Плюс для команды: понятно, где искать запрос, тип, store или страницу. Цена выбора: один сценарий проходит через несколько папок, поэтому используем согласованные имена и явные зависимости. Новые слои и пустые каталоги заранее не создаём.

`pages` собирают экраны; `components` отвечают за отображение и взаимодействие. Большие карты и панели разделены на небольшие файлы. Данные заявок, координаты, представители и предопределённые назначения находятся в `api/mock/data.ts`, тестовые пользователи — отдельно в `config/demoUsers.ts`. Обычные подписи «Загрузить заявки» и тексты пустых состояний допустимы прямо в компоненте: это UI, а не бизнес-данные.

Общий `compose.yaml` находится на уровень выше, в корне RouteRoad. Сейчас в нём
один frontend-сервис с production Nginx; остальные сервисы появятся при интеграции.
Разработка запускается локальным Vite, dev-контейнера нет. Dockerfile содержит
стадии dependencies → build → production. UI-иконки — `lucide-react` через `Icon`;
отдельный SVG-файл сохранён для favicon.

### Допустимые зависимости

```text
main → routes → pages / components/layout
pages / компоненты-контейнеры → stores / hooks → api → types / utils
визуальные компоненты → props / types / utils / components/ui
```

`api` не импортирует store, страницы или React. `stores` не импортируют JSX и не содержат HTTP-код. `types` не имеют runtime-логики. `utils` не вызывают API и не управляют store. Страницы не импортируют друг друга; циклы запрещены. Тип интерфейса `WorkdayApi` используется адаптером через `import type`, без обратной runtime-зависимости. Alias `@/` указывает на `src/` в Vite и TypeScript.

## 3. Рабочий день: пусто → загрузка → построение

| Момент                                         | Данные и интерфейс                                                                                         |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Первый запуск / перезагрузка / «Очистить день» | Нет заявок, представителей, офиса и маршрутов; пустые состояния, построение недоступно                     |
| «Загрузить заявки»                             | Отдельная async-операция: 18 заявок `new` без назначений, 6 представителей, офис; маршрутов ещё нет        |
| «Построить маршруты»                           | Вторая async-операция: 6 планов, 18 назначенных заявок, 0 завершённых; появляется расписание представителя |
| Дальнейшие действия                            | Локальные статусы, переназначение и история через тот же адаптер; это демонстрация, без сервера            |

Конкретный поток загрузки:

```text
Button в WorkdayToolbar
  → stores/workdayStore.ts: loadRequests()
  → api/workdayApi.ts: workdayApi.loadRequests()
  → api/mock/demoWorkdayApi.ts
  → Promise<WorkdaySnapshot>
  → store обновляет снимок → подписанные компоненты перерисовываются
```

`loadRequests`, `buildRoutes`, `setVisitStatus`, `reassignVisit` возвращают типизированный снимок; `reset` очищает адаптер. Store хранит `loadStatus`, `planStatus`, общую ошибку и `pendingVisitId`, блокирует конкурирующие изменения. При отказе сохраняются предыдущие данные и возможность повтора. Сброс меняет поколение и в store, и в адаптере: запоздалый ответ старой операции не восстанавливает очищенный день.

Фабрики `createWorkdayStore(api, context?)` и `createDemoWorkdayApi({ latencyMs, failOperation, wait })` позволяют проверить ошибки, повтор и сброс во время ожидания без глобальных тестовых hooks. Провайдер демоавтора передаётся отдельно, фабрика store сама не читает демосессию. Адаптер возвращает копии; UI не меняет его внутренние данные по ссылке. Демопереходы проверяются в адаптере, а не дублируются в каждой кнопке.

Для «Прибыл» путь аналогичен: `VisitActionPanel → workdayStore.setVisitStatus → workdayApi → demoWorkdayApi → snapshot → VisitStatusBadge`. Общая отметка тестового режима отличает этот сценарий от реального сервера. Переход `assigned → en-route → arrived → in-progress → completed` — ограничение текущего примера, не согласованная машина Java.

При интеграции заменим адаптер за `WorkdayApi`, добавим HTTP-клиент и проверку JSON
как `unknown`. Java вернёт заявки, маршруты, алерты и агрегаты для экранов;
адаптер преобразует DTO в UI-модели. Таблицы `planning_run`/`route_stop` не обязаны
появляться в stores один к одному. Выбранные ответы, команды, cookie-сессия и
длительные операции описаны в `frontend-api.md`. Браузер обращается только к Java,
не к Python или БД. Текущий полный demo snapshot при интеграции заменяется
отдельными загрузками сводки, списков и деталей.

## 4. Роли и виды состояния

`routes/index.tsx` направляет демопользователя в `/dispatcher` либо `/representative`; `ProtectedRoute` проверяет выбранную роль. `DispatcherLayout` и `RepresentativeLayout` дают независимые меню и оболочки. Прямой переход в чужой раздел показывает запрет. Реальные права на каждую операцию позднее проверяет Java.

| Состояние                               | Где живёт сейчас                                                                     |
| --------------------------------------- | ------------------------------------------------------------------------------------ |
| Выбранная демороль                      | `sessionStore`, роль и изменённые имена в `sessionStorage`; остальное из `demoUsers` |
| Снимок рабочего дня                     | Память demo API и read model в `workdayStore`; оба сбрасываются при перезагрузке     |
| Выбор представителя, поиск, уведомление | `workdayStore`; меню — `uiStore`                                                     |
| Поле формы, раскрытая локальная панель  | `useState` рядом с компонентом                                                       |
| Долговременное расписание и очередь     | Пока отсутствуют; будущая IndexedDB                                                  |

Выбор роли временный и явно подписан. Смена роли в этой вкладке сохраняет подготовленный демонстрационный день; перезагрузка и очистка начинают пустой. Не включаем `persist` всего Zustand и не выдаём локальную роль за серверную сессию. После подключения Java отдельно выберем управление серверным кешем; TanStack Query остаётся кандидатом, не установленной частью этого решения.

## 5. Интерактивная карта

Leaflet 1.9.4 и React Leaflet 5 заменяют статическое изображение. `WorkdayMap` получает заявки с `location`, офис и `routes` через props; поддерживает перемещение, масштаб, маркеры, popup, выбор встречи и показ всех точек. Компонент не назначает представителей и не строит геометрию. [Leaflet](https://leafletjs.com/reference.html), [React Leaflet](https://react-leaflet.js.org/docs/start-introduction/).

`RoutePlan.geometry` — GeoJSON `LineString`, координаты **`[longitude, latitude]`**. На границе Leaflet переводим их в `[latitude, longitude]`. Демоадаптер соединяет офис и остановки прямыми отрезками, используя заранее заданное распределение; это не дорожный маршрут, оптимизатор, геокодирование или проверка временных окон. Геометрию настоящего маршрута позднее предоставит Java API.

Подложка по умолчанию — HTTPS-тайлы OpenStreetMap с видимой атрибуцией. `config/map.ts` принимает публичный `VITE_MAP_TILE_URL`; при смене поставщика нужно обновить атрибуцию и проверить условия. Загрузка подложки требует сети; ошибки и повтор показаны отдельно, список встреч остаётся доступен. Массовую загрузку тайлов и офлайн-карту не реализуем. [OSM tile usage policy](https://operations.osmfoundation.org/policies/tiles/).

## 6. Будущие PWA и IndexedDB

IndexedDB остаётся **планом**, а не удалённым требованием. Это браузерная транзакционная БД для сохранённого расписания/маршрутов и outbox действий представителя. Zustand хранит оперативное состояние, IndexedDB должна переживать перезапуск. Service worker и manifest обеспечат установку/запуск оболочки; они сами не сохраняют рабочий день и не реализуют синхронизацию. [MDN: IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API).

Будущий поток без связи: открыть ранее сохранённый снимок → записать действие в outbox → после успешной транзакции показать «сохранено на устройстве» → повторить с постоянным action ID при восстановлении связи → сохранить канонический ответ и убрать подтверждённую команду одной транзакцией. Локальное намерение отделяется от серверного статуса. При конфликте данные не перезаписываются молча.

## 8. Проверка границ компонентов — 09.11.2026

Группировка остаётся по назначению, без новой иерархии atoms/molecules:

- `ui` — общие элементы, включая PageHeader и EmptyState; получают props.
- `layout` — оболочки ролей и навигация; могут читать stores.
- `map` — Leaflet и взаимодействие с картой; бизнес-данные приходят через props.
- `profile` — профиль и демосессия; `workday` — общие предметные элементы.
- `dispatcher` / `representative` — предметные панели и их контейнеры.

WorkdayFeedback отдельно читает сообщения/действия store; общий PageHeader
ничего о рабочем дне не знает. DaySummary получает готовые counts: сейчас их
вычисляет контейнер, позже Java. ReassignDrawer получает детали через props.
VisitAssignment управляет открытием, загрузкой по ID и назначением; данные
приходят через useVisitDetails → API. Карточка, ссылка из истории и popup карты
не требуют наличия заявки в текущем глобальном списке. Старые ответы после
закрытия, выбора другой заявки, смены revision или повтора не применяются.

RepresentativeSchedule вынесен из страницы в контейнер списка. В VisitsTable
нет второго локального поиска: отображается уже отфильтрованная API-страница.
Выбор представителя сохраняет ID независимо от того, находится ли карточка
в глобальном демоснимке. ESLint запрещает stores/API в `ui`, `map`, DaySummary
и ReassignDrawer, а обратные зависимости UI — в API и utils.

## 9. Как подключать Java и проверять без него

Текущая организация подходит для постепенной интеграции, но WorkdayApi пока
имеет демосигнатуры. Мутации возвращают полный WorkdaySnapshot, reset синхронный;
MeetingPage, данные контекста алертов и обзор карты ещё используют снимок.
Сессия также демонстрационная. Заполнить URL и получить всю интеграцию нельзя.

Порядок подключения:

1. В `api` добавить HTTP-клиент и адаптер первой цепочки «список → детали»:
   внешний JSON проверяется, DTO преобразуется в UI-типы, ошибки видны экрану.
2. Отдельно подключить сводку, карту, расписание, контекст алертов и кандидатов
   назначения. Не вычитывать все серверные страницы ради прежнего snapshot.
3. Команды переводятся на результат заявки / operation_id, ожидание активации
   и обновление затронутых запросов; reset становится асинхронным.
4. Подключить настоящую сессию, обработку 401/403, версии и доступные действия,
   остановки OFFICE, модельную скорость и групповые алерты по контракту.

Фасад `api/workdayApi.ts` остаётся точкой выбора источника; HTTP-адаптер и demo
работают с одним UI-контрактом после соответствующего шага. HTTP-сбой не должен
автоматически заменяться успешным демоответом.

Сейчас локально достаточно `npm run dev`. DEV-переменные
`VITE_DEMO_LATENCY_MS` и `VITE_DEMO_FAIL_ONCE` позволяют проверить ожидание,
ошибку/повтор чтения и изменения, а сброс заново включает первые ошибки.
Параллельные одинаковые чтения объединяются только пока запрос ожидается;
это сохраняет видимую первую ошибку и при StrictMode. Production их не использует.
DevTools Offline не отключает Promise-источник демо и не доказывает офлайн-PWA.

Когда появится HTTP-клиент, для работы без Java можно включить
[MSW](https://mswjs.io/docs/) с ответами того же контракта: приложение будет
использовать настоящий клиент, а запросы перехватятся в браузере. Сейчас MSW
не установлен, поскольку бизнес-HTTP ещё нет. Локальную Java можно будет
подключить через [Vite proxy](https://vite.dev/config/server-options.html#server-proxy)
для `/api`, сохранив относительные пути и общую origin-сессию.
