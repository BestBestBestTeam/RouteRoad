# RouteRoad: сущности и API для Java

Единый результат задачи по проектированию API фронтенда, 08.11.2026.
Сначала описаны все обновлённые сущности и объекты ответов, затем HTTP-ручки.
Документ содержит необходимые определения без обращения к другим файлам.
Это контракт для реализации; HTTP-интеграция пока не подключена.
Все HTTP-пути ниже имеют общий префикс `/api`.

## 1. Сущности

Ниже полный состав данных для Java API: семь исходных сущностей и дополнения.
Java владеет схемой общей БД и миграциями. Python читает общую БД; записывает
только сущности плана. PWA получает данные через Java. Python-симулятор использует
те же Java-ручки, тела запросов и проверки, что PWA; внутренний Python-расчётчик
вызывается Java. Новые поля и сущности здесь являются требованиями к реализации,
а не уже существующими миграциями.

Блоки «Добавилось» показывают отличия от исходного контракта Java/Python.
Для новых сущностей добавлен весь набор полей; ниже указано, каким ручкам он нужен.

### 1.1. Формат и общие типы

- `UUID` — строка UUID; `date` — `YYYY-MM-DD`; `timestamp` — ISO 8601 с зоной.
- `int` — целое; `number` — число; `bool` — логическое значение;
  `JSON` — JSON-значение. `null` допустим только там, где указан явно.
- Координаты WGS84 — `lat` от -90 до 90, `lon` от -180 до 180;
  расстояния — метры; длительности — секунды.
- `Position = {lat: number, lon: number, at: timestamp}` — последнее измерение.
- `Actor = {id: UUID|null, name: string, role: dispatcher|representative|system}`.
  Для системы `id=null`, `name="Система"`; для человека источник — `app_user`.
- `Geometry = {type: "LineString", coordinates: [number, number][]}` — GeoJSON,
  порядок пары `[lon, lat]`. `geometry_kind=straight|road` сообщает источник линии.
- `Change = {field: string, before: JSON, after: JSON}` — изменение поля;
  значения могут быть `null`. Человеческую подпись поля задаёт словарь Java/UI.
- `PlanningMetrics = {total_distance_m: int, violated_windows: int,
unassigned_count: int, solve_time_ms: int}` — метрики результата расчёта Python.

### 1.2. `service_order` — заявка

Хранится в БД, пишет Java. Адрес, район и продукт приходят из синтетического
сценария; номер выдаёт Java. Это расширение исходной заявки.

- `id: UUID` — первичный ключ.
- `number: string` — стабильный уникальный номер для показа и поиска; новое поле.
- `client_name: string` — имя клиента.
- `address: string` — адрес встречи; новое поле.
- `district: string|null` — район, если известен; новое поле.
- `product: string` — название продукта доставки; новое поле.
- `lat, lon: number` — координаты встречи.
- `window_from, window_to: timestamp` — окно, в которое встреча должна начаться.
- `service_duration_s: int` — длительность встречи, больше нуля.
- `status: OrderStatus` — текущее состояние заявки.
- `service_date: date` — текущий день выполнения.
- `version: int` — версия, увеличивается при изменениях, влияющих на состояние
  или назначение, в том числе при отказе до изменения самого статуса.

**Добавилось:**

- `number` — нужно для `GET /orders`, `GET /orders/{id}` и `GET /workday/map`:
  показывать номер заявки и искать по нему в списке.
- `address` — нужно для `GET /orders`, `GET /orders/{id}` и `GET /workday/map`:
  показывать адрес встречи в списке, карточке и popup карты.
- `district` — нужно для `GET /orders` и `GET /orders/{id}`:
  показывать район встречи.
- `product` — нужно для `GET /orders/{id}`: показывать продукт доставки.

`OrderStatus`: `NEW`, `ASSIGNED`, `UNASSIGNED`, `EN_ROUTE`, `ARRIVED`,
`IN_PROGRESS`, `COMPLETED`, `RESCHEDULED`, `CANCELLED`.
При переносе Java сохраняет событие с прежней/новой датой, меняет `service_date`
на следующий день и возвращает текущий `status` в `NEW`.

### 1.3. `courier` — представитель

Хранится в БД, пишет Java. Имя, офис и смена приходят из сценария; позицию
отправляет PWA или симулятор одной и той же ручкой.

- `id: UUID` — первичный ключ.
- `name: string` — имя представителя в команде.
- `office_id: UUID` — ссылка на свой `office`.
- `shift_start, shift_end: timestamp` — границы смены.
- `position: Position|null` — последняя полученная позиция.
- `is_available: bool` — доступен для новых назначений в `availability_date`;
  нахождение внутри смены проверяется отдельно.
- `availability_date: date` — дата действия флага; новое поле.

**Добавилось:**

- `availability_date` — нужно для `POST /couriers/{id}/refusal`, `GET /couriers`
  и `GET /couriers/{id}/schedule`: применять отказ на день к правильной дате
  и не переносить недоступность на следующий день.

Отказ от одной заявки не меняет доступность. Отказ от всех оставшихся на день
ставит `is_available=false` и сохраняется событием `COURIER_REFUSED` с датой.
При переходе к новому модельному дню Java пересчитывает флаг для новой даты;
вчерашний отказ не переносится автоматически. Для запроса другого дня Java
восстанавливает дневную доступность по событиям этого дня.

### 1.4. `office` — офис

Хранится в БД, пишет Java; источник — сценарий. В MVP один офис.

- `id: UUID` — первичный ключ.
- `name: string` — название.
- `address: string` — адрес для карточки офиса; новое поле.
- `lat, lon: number` — координаты.

**Добавилось:**

- `address` — нужно для `GET /workday`, `GET /workday/map`
  и `GET /couriers/{id}/schedule`: показывать адрес получения карт.

### 1.5. `planning_run` — запуск расчёта

Хранится в БД, добавляет Python. Каждому успешному `/assign` или `/reassign`
соответствует один запуск. Повтор запроса с тем же `request_id` возвращает его
прежний результат. Java создаёт новые ID для новых попыток пересчёта.

- `plan_version: int` — глобальная возрастающая версия запуска, первичный ключ.
- `request_id: UUID` — уникальный идентификатор запроса Java к расчётчику.
- `run_type: ASSIGN|REASSIGN` — первоначальный расчёт или перерасчёт.
- `event_type: PlanningEventType|null` — причина перерасчёта, иначе `null`.
- `algorithm: greedy|ortools` — алгоритм.
- `plan_date: date` — рассчитанный день.
- `model_now: timestamp` — модельное время запроса.
- `created_at: timestamp` — модельное время создания записи.
- `metrics: PlanningMetrics` — новое поле; метрики результата, включая измеренное
  время расчёта, сохраняются для повторного ответа с тем же `request_id`.

**Добавилось:**

- `metrics` — нужно для `GET /operations/{id}`: возвращать сохранённые показатели
  построения/перерасчёта, включая время расчёта, даже при повторном запросе.
- Значение `ORDER_REFUSED` в `event_type` — нужно для `POST /orders/{id}/refusal`:
  отличать перерасчёт после отказа от одной заявки от отказа на весь день.
  Это новое значение перечисления, а не отдельная колонка.

`PlanningEventType`: `CLIENT_CANCELLED`, `ORDER_REFUSED`, `COURIER_REFUSED`,
`COURIER_DELAYED`, `AUTO_REASSIGN_REQUEST`, `MANUAL_REASSIGN`.
`ORDER_REFUSED` добавляется для отказа от одной заявки; `COURIER_REFUSED`
означает отказ от остальных заявок представителя в выбранный день.

### 1.6. `route` — маршрут представителя на день

Хранится в БД, добавляет Python с `is_active=false`. Только Java меняет активность.

- `id: UUID` — первичный ключ.
- `courier_id: UUID` — представитель.
- `plan_date: date` — день маршрута.
- `plan_version: int` — ссылка на создавший маршрут `planning_run`.
- `is_active: bool` — активирован ли маршрут Java.
- `algorithm: greedy|ortools` — алгоритм построения.
- `total_distance_m: int` — суммарное расстояние, не меньше нуля.
- `violated_windows: int` — число нарушенных окон, не меньше нуля.
- `created_at: timestamp` — модельное время построения.

Уникальность активного маршрута: `(courier_id, plan_date) WHERE is_active`.
При частичном пересчёте меняются маршруты только затронутых представителей.
Актуальный день включает все активные маршруты, в том числе разных `plan_version`.

### 1.7. `route_stop` — остановка маршрута

Хранится в БД, добавляет Python. Первичный ключ — `(route_id, sequence)`.

- `route_id: UUID` — ссылка на маршрут.
- `sequence: int` — порядок остановки, начиная с 1.
- `type: OFFICE|ORDER` — офис или встреча.
- `order_id: UUID|null` — ссылка на заявку только для `ORDER`.
- `office_id: UUID|null` — ссылка на офис только для `OFFICE`.
- `arrival_eta, departure_eta: timestamp` — плановые прибытие и отъезд.
- `distance_from_prev_m: int` — расстояние от предыдущей остановки; у первой 0.
- `window_violation_s: int` — нарушение окна в секундах; 0, если его нет.

Ровно одна из ссылок `order_id`/`office_id` заполнена и соответствует `type`.
Первая остановка — офис; заезды за новыми картами — отдельные остановки.
Порядок и ETA берутся отсюда, а не сортировкой по окну заявки.

### 1.8. `assignment` — решение по заявке

Хранится в БД, добавляет Python; старые решения не удаляются. Уникальная пара —
`(order_id, plan_version)`. Решение может содержать обоснованный отказ в назначении.

- `order_id: UUID` — заявка.
- `courier_id: UUID|null` — назначенный представитель; `null`, если не назначено.
- `route_id: UUID|null` — маршрут назначения; `null`, если не назначено.
- `plan_version: int` — ссылка на запуск расчёта.
- `source_order_version: int` — версия заявки, по которой выполнен расчёт.
- `reason_code: AssignmentReason` — код объяснения.
- `reason_text: string` — объяснение для диспетчера.
- `decided_by: SYSTEM|DISPATCHER` — алгоритм/таймаут или ручной выбор диспетчера.
- `created_at: timestamp` — модельное время решения.

`AssignmentReason`: `NEAREST`, `FREE_WINDOW`, `OPTIMIZED`,
`REASSIGNED_AFTER_REFUSAL`, `MANUAL_DISPATCHER`, `AUTO_AFTER_TIMEOUT`,
`NO_CAPACITY`, `WINDOW_INFEASIBLE`, `DEFER_NEXT_DAY`.
У неназначенного решения обе ссылки `courier_id`/`route_id` равны `null`.

**Уточнено:**

- `route_id` допускает `null` — нужно для `GET /orders` и `GET /orders/{id}`:
  возвращать причину невозможности назначения, когда маршрута нет.
  Само поле уже было в исходном контракте.

Python записывает запуск, маршруты, остановки и назначения одной транзакцией.
Java перед активацией повторно проверяет версии, дневную доступность и запреты
после отказов, затем атомарно переключает маршруты и записывает `PLAN_ACTIVATED`.
Текущие назначения выбираются только из подтверждённых таким событием запусков,
включая неназначенные решения без маршрута. Самая большая записанная версия
без подтверждения Java не является текущей.

### 1.9. `app_user` — учётная запись

Новая сущность БД, пишет Java. Нужна для входа, прав, профиля и автора действий.

- `id: UUID` — первичный ключ.
- `login: string` — уникальный логин.
- `password_hash: string` — хеш пароля; никогда не возвращается в API.
- `name: string` — имя профиля, 2–64 символа.
- `role: dispatcher|representative` — роль, назначает Java.
- `courier_id: UUID|null` — представитель аккаунта; обязателен для роли
  `representative`, у диспетчера `null`; одна такая связь на представителя.

Имя профиля и `courier.name` имеют разные назначения; изменение профиля
не изменяет личность представителя или его маршруты. Cookie-сессию и CSRF
обслуживает стандартный механизм Java, данные сессии не являются публичным DTO.

**Добавилось (новая сущность целиком):**

- `id`, `login`, `password_hash` — нужны для `POST /auth/login`:
  найти аккаунт, проверить пароль и связать с ним сессию.
- `name` — нужно для `GET /me` и `PATCH /me`: показывать и сохранять имя профиля.
- `role`, `courier_id` — нужны для `GET /me` и `POST /orders/{id}/status`:
  определить роль и проверить, что представитель меняет свою заявку.

### 1.10. `business_event` — бизнес-событие и аудит

Новая сущность БД, пишет Java одной транзакцией с бизнес-изменением.

- `id: UUID` — первичный ключ.
- `type: BusinessEventType` — код бизнес-события.
- `service_date: date` — день, к которому относится событие.
- `order_id: UUID|null` — одна заявка, если событие относится к ней.
- `courier_id: UUID|null` — связанный представитель.
- `actor_id: UUID|null` — пользователь; `null` для системы.
- `occurred_at: timestamp` — когда действие совершено по модельным часам.
- `created_at: timestamp` — когда Java приняла событие по модельным часам.
- `reason: string` — причина действия.
- `payload: object` — данные события: версии, `changes: Change[]`, ссылки на
  команду/алерт, `order_ids: UUID[]`, `plan_version: int` по типу события.

`BusinessEventType`: `DATA_LOADED`, `PLAN_ACTIVATED`, `STATUS_CHANGED`,
`ASSIGNMENT_CHANGED`, `ORDER_RESCHEDULED`, `COURIER_DELAYED`, `ORDER_REFUSED`,
`COURIER_REFUSED`, `ALERT_CREATED`, `ALERT_ORDER_RESOLVED`, `ALERT_RESOLVED`,
`SCENARIO_RESET`. Это внутренние коды аудита Java; `HistoryEntry.type`
отображает их в перечисленные ниже категории интерфейса.

Для переноса `payload` обязательно содержит `from_date`, `to_date` и прежнее/новое
состояние; это сохраняет результат в истории исходного дня. `PLAN_ACTIVATED`
содержит `plan_version` и `order_ids`. При отказе от заявки сохраняется пара
`order_id`/`courier_id`; при отказе на день — представитель и все затронутые ID.
Python читает эти ограничения при каждом расчёте, включая ручное переназначение.
Отдельная таблица отказов для MVP не нужна.

**Добавилось (новая сущность целиком):**

- `id`, `type`, `service_date` — нужны для `GET /history`:
  идентифицировать события, фильтровать по типу и рабочему дню.
- `order_id`, `courier_id` — нужны для `GET /history`,
  `POST /orders/{id}/refusal` и `POST /couriers/{id}/refusal`:
  связать историю и ограничения назначения с конкретной заявкой/представителем.
- `actor_id` — нужно для `GET /history`: показывать автора изменения.
- `occurred_at`, `created_at` — нужны для `GET /history`:
  сохранять время действия и время его приёма Java, включая действия после офлайна.
- `reason`, `payload` — нужны для `GET /history` и `GET /orders`:
  показывать причины и изменения до/после, а также перенос с исходного дня на новый.

### 1.11. `alert` — алерт и общий срок решения

Новая сущность БД, пишет Java. Отказ одной заявки и отказ на день различаются
полем `scope`, при этом используют общий жизненный цикл.

- `id: UUID` — первичный ключ.
- `source_event_id: UUID` — событие, вызвавшее алерт.
- `service_date: date` — день алерта.
- `courier_id: UUID|null` — представитель, от которого пришло сообщение.
- `kind: delay|refusal|conflict` — задержка, отказ или конфликт.
- `scope: order|courier_day` — одна заявка или группа оставшихся заявок на день.
- `severity: warning|critical` — важность.
- `status: open|resolved` — общее состояние алерта.
- `reason_code, reason_text: string` — код и объяснение причины.
- `created_at, deadline_at: timestamp` — создание и срок реакции по модельным часам.
- `resolved_at: timestamp|null` — когда закрыт весь алерт.
- `resolved_by: UUID|null` — пользователь, закрывший весь алерт, либо система.
- `resolution_reason: string|null` — итоговое объяснение.

Срок решения — 10 модельных минут. До него решения принимает диспетчер; затем
Java запускает автоматическое решение оставшихся заявок. `IN_PROGRESS` и
`COMPLETED` не входят в группу переназначения. Начатую встречу представитель
сохраняет и может завершить даже после отказа на день.

**Добавилось (новая сущность целиком):**

- `id`, `source_event_id` — нужны для `GET /alerts`:
  идентифицировать алерт и связать его с вызвавшим событием.
- `service_date`, `courier_id` — нужны для `GET /alerts`:
  выбрать алерты дня и показать связанного представителя.
- `kind`, `scope`, `severity`, `status` — нужны для `GET /alerts`:
  отличать одиночный отказ от отказа на день, показывать тип/важность и фильтровать список.
- `reason_code`, `reason_text` — нужны для `GET /alerts`:
  объяснять, что произошло и почему требуется решение.
- `created_at`, `deadline_at` — нужны для `GET /alerts`
  и `POST /alerts/{id}/auto-reassignment`: показывать таймер и запускать
  автоматическое решение по сроку на Java.
- `resolved_at`, `resolved_by`, `resolution_reason` — нужны для `GET /alerts`:
  показывать время, автора и результат обработки.

### 1.12. `alert_order` — заявки алерта и их отдельные решения

Новая сущность БД, пишет Java. Первичный ключ — `(alert_id, order_id)`.

- `alert_id: UUID` — ссылка на алерт.
- `order_id: UUID` — затронутая заявка.
- `status: pending|resolved` — осталось ли принять решение по этой заявке.
- `resolved_at: timestamp|null` — время решения.
- `resolved_by: UUID|null` — пользователь, принявший решение, либо система.
- `resolution_reason: string|null` — назначение, перенос или другой результат.

У одиночного отказа одна запись, у отказа на день — несколько. Ручное решение
одной заявки закрывает только её запись. Общий алерт закрывается, когда обработаны
все его заявки. При нескольких решавших пользователях детали берутся из этих
записей и аудита; общий `resolved_by` — автор последнего решения.

**Добавилось (новая сущность целиком):**

- `alert_id`, `order_id` — нужны для `GET /alerts`
  и `POST /orders/{id}/reassignment`: связать групповой алерт с его заявками.
- `status` — нужно для `POST /alerts/{id}/auto-reassignment`:
  обрабатывать только заявки, по которым решение ещё не принято.
- `resolved_at`, `resolved_by`, `resolution_reason` — нужны для `GET /alerts`:
  показывать отдельное решение по каждой заявке и закрывать весь алерт после всех решений.

### 1.13. `api_command` — идемпотентная команда и длительная операция

Новая сущность БД, пишет Java. Покрывает прямые команды, действия `/sync`
и `/operations/{id}`; не требуется отдельная таблица на каждую ручку.

- `id: UUID` — ID команды; его же API возвращает как `operation_id`.
- `scenario_id: UUID` — поколение сценария, к которому относится команда.
- `actor_id: UUID|null` — пользователь, либо система.
- `idempotency_key: UUID` — постоянный ID действия клиента или системы.
- `type: string` — вид команды.
- `request_hash: string` — хеш логической операции, сценария, цели и параметров.
- `request: object` — сохранённые параметры команды.
- `status: pending|running|succeeded|failed` — состояние выполнения.
- `result: JSON` — результат либо `null` до успеха.
- `error: {code: string, message: string, details: JSON}|null` — причина отказа.
- `created_at, updated_at: timestamp` — модельные времена команды.

Ключ уникален в контексте автора, включая системного автора. Совпавший ключ
с другой логической командой или параметрами даёт 409. Перед проверкой действия
из `/sync` Java преобразует их в те же команды статуса, что прямой запрос:
различие внешних HTTP-путей не должно создавать ложный конфликт дубликатов.
`client_action_id` из sync — тот же ключ, который использовался при прямой
отправке этого действия. Бизнес-эффект и результат
команды фиксируются согласованно. Сброс инвалидирует команды старого сценария,
но сохраняет их ключи/результаты, чтобы потерянный ответ не вызвал повторный reset.

**Добавилось (новая сущность целиком):**

- `id`, `status`, `result`, `error` — нужны для `GET /operations/{id}`:
  отслеживать выполнение команды и получать её результат или ошибку.
- `scenario_id` — нужно для `POST /demo/reset`:
  инвалидировать ожидающие команды прошлого сценария.
- `actor_id`, `idempotency_key`, `request_hash` — нужны для
  `POST /orders/{id}/status` и `POST /sync`: распознавать повторы одного действия
  и не применять его дважды; другой запрос с тем же ключом отклонять.
- `type`, `request` — нужны для `POST /planning-jobs`:
  сохранить вид и параметры принятой команды для асинхронного выполнения.
- `created_at`, `updated_at` — нужны для `GET /operations/{id}`:
  учитывать время создания и изменения состояния команды на стороне Java.

### 1.14. `scenario_state` — сценарий и модельные часы

Новая сущность БД, пишет Java. Одна активная запись для текущего учебного сценария.

- `scenario_id: UUID` — идентификатор поколения; меняется при сбросе.
- `seed: int|null` — фактически использованный seed; `null` до первой генерации.
- `config: object` — параметры генерации и расчёта.
- `service_date: date` — текущий модельный день.
- `model_anchor_at: timestamp` — модельное время в опорный момент.
- `real_anchor_at: timestamp` — реальное время того же момента.
- `speed: number` — скорость модельного времени, не меньше 0; 0 означает паузу.
- `revision: int` — версия настройки часов, растёт при изменении времени/скорости.

Текущий `clock.now` Java вычисляет по опорным временам и скорости. Это служебное
состояние позволяет восстановить сценарий после рестарта; `planning_run.model_now`
хранит лишь время конкретного расчёта и не является текущими часами.

**Добавилось (новая сущность целиком):**

- `scenario_id` — нужно для `POST /demo/reset`:
  менять поколение сценария и защищать новое состояние от старых команд.
- `seed`, `config` — нужны для `POST /demo/scenarios` и `POST /planning-jobs`:
  воспроизводить генерацию и сохранять настройки генератора/расчётчика.
- `service_date` — нужно для `GET /workday`:
  определять текущий модельный день, если дата запроса не указана.
- `model_anchor_at`, `real_anchor_at`, `speed`, `revision` — нужны для
  `GET /workday` и `GET /couriers/{id}/schedule`: возвращать согласованные
  модельные часы для расписания и таймеров, в том числе после рестарта Java.

### 1.15. Объекты ответа API

Это DTO из перечисленных данных, а не дополнительные таблицы.

- `UserView`: `id: UUID`, `name: string`, `role: dispatcher|representative`,
  `courier_id: UUID|null` из `app_user`; `csrf_token: string` из механизма сессии.
- `Clock`: `scenario_id: UUID`, `now: timestamp`, `speed: number`, `revision: int`
  из `scenario_state`. Поколение используется заголовком `X-Scenario-ID` команд.
- `OrderView`: все публичные поля `service_order`; `day_status: OrderStatus`
  для выбранного дня, `assignment: AssignmentView|null`, `available_actions: string[]`.
  Перенесённая с выбранного дня заявка имеет `day_status=RESCHEDULED`, хотя
  текущие `status=NEW` и `service_date` уже относятся к следующему дню.
- `AssignmentView`: поля `assignment` плюс `courier_name: string|null` из `courier`
  и `actor: Actor` из подтверждённого события/команды Java. Для новой заявки
  `assignment=null`; для неназначенного решения объект с причиной и пустыми ссылками.
- `CourierView`: поля `courier` плюс `total_orders: int`, `completed_orders: int`,
  `open_alert_count: int`, `available_actions: string[]`. Счётчики Java вычисляет
  за выбранный день по всей выборке, а дневную доступность — по событиям дня.
- `OfficeView`: публичные поля `office`.
- `RouteView`: поля `route`, `stops: RouteStop[]` из `route_stop`,
  `geometry: Geometry`, `geometry_kind: straight|road`. Java строит прямую линию
  по координатам остановок; дорожную геометрию предоставляет подключённый источник.
- `RouteStop`: публичные поля `route_stop` с указанными выше типами; координаты
  точки берутся из связанной заявки или офиса, дублировать их в БД не требуется.
- `AlertView`: поля `alert` плюс `order_ids: UUID[]`,
  `orders: {order_id: UUID, status: pending|resolved, resolution: Resolution|null}[]`
  из `alert_order`; `title: string`, `impact: string[]`,
  `resolution: Resolution|null`, `available_actions: string[]` формирует Java.
- `Resolution = {at: timestamp, actor: Actor, reason: string}` — итог из полей
  решения и аккаунта автора; `null`, если решение ещё не принято.
- `HistoryEntry`: `id: UUID`, `type: string`, `created_at: timestamp`, `actor: Actor`,
  `order_id: UUID|null`, `alert_id: UUID|null`, `title: string`,
  `description: string`, `reason: string`, `changes: Change[]`. Java строит из
  `business_event` и связанных записей. Типы для UI: `data_loaded`, `routes_built`,
  `status_changed`, `assignment_changed`, `alert_created`, `alert_resolved`.
- `OperationView`: `id: UUID`, `status: pending|running|succeeded|failed`,
  `result: JSON`, `error: Error|null`, `clock: Clock` из `api_command` и часов.
  Успех расчёта означает активацию Java, а не только запись Python.
- `Error = {code: string, message: string, details: JSON}` — единая ошибка Java.
- `Page<T> = {items: T[], total: int, page: int, page_size: int, clock: Clock}` —
  результат серверной фильтрации/пагинации. `page` начинается с 1, размер 1–100,
  по умолчанию 10; `total` относится ко всей отфильтрованной выборке.

### 1.16. Составные ответы и действия синхронизации

- `WorkdayView = {date: date, counts: WorkdayCounts, has_routes: bool,
offices: OfficeView[], clock: Clock}` — сводка выбранного дня.
- `WorkdayCounts = {orders_total: int, orders_assigned: int,
orders_completed: int, couriers_total: int, open_alerts: int}`. Источник — Java
  по всей выборке дня, включая его сохранённые результаты переноса, а не по странице.
- `MapView = {orders: MapOrder[], couriers: MapCourier[], offices: OfficeView[],
routes: MapRoute[], alerts: MapAlert[], clock: Clock}` — общий срез карты.
  `MapOrder` содержит `id, number, address, client_name, lat, lon, day_status`
  из `OrderView`; `MapCourier` — `id, name, position` из `CourierView`;
  `MapRoute` — `id, courier_id, plan_version, stops, geometry, geometry_kind`
  из `RouteView`; `MapAlert` — `id, order_ids, courier_id` из открытого `AlertView`.
  Типы и nullable этих полей совпадают с исходными DTO.
- `OperationAccepted = {operation_id: UUID, clock: Clock}` — приём долгой команды.
- `PlanningResult = {plan_version: int, affected_courier_ids: UUID[],
metrics: PlanningMetrics}` — версия, представители маршрутов этого запуска
  и сохранённые метрики `planning_run` после активации Java.
- `ScenarioLoadResult = {seed: int, orders_count: int, couriers_count: int}` —
  seed из `scenario_state`, количества реально загруженных заявок и представителей.
- `ScenarioResetResult = {scenario_id: UUID}` — новое поколение сценария.
- `DelayResult = {alert_id: UUID|null}` — созданный Java алерт либо отсутствие
  необходимости в решении диспетчера.
- `StatusResult = {result: APPLIED|DUPLICATE, order: OrderView, clock: Clock}` —
  подтверждённое состояние после прямой команды статуса.
- `SyncAction = {client_action_id: UUID, order_id: UUID, status: OrderStatus,
occurred_at: timestamp, base_version: int, reason?: string}` — данные,
  сохранённые PWA/симулятором в момент действия. Представителя Java берёт из сессии.
- `SyncItemResult = {client_action_id: UUID, result: APPLIED|DUPLICATE|CONFLICT,
order: OrderView|null, reason: string|null}` — результат одного действия.
  При недоступной или отсутствующей заявке `order=null`; причина конфликта заполнена.
- `SyncResult = {results: SyncItemResult[], clock: Clock}` — итог отправки пачки.

`OperationView.result` для соответствующих команд содержит `PlanningResult`,
`ScenarioLoadResult`, `ScenarioResetResult` или `DelayResult`; до готовности — `null`.

`available_actions` вычисляет Java по пользователю, состоянию и ограничениям,
а не получает из клиента. У заявки это допустимые коды переходов статуса,
`REPORT_DELAY`, `REFUSE_ORDER`, `REASSIGN`; у представителя — `REFUSE_WORKDAY`;
у алерта — `REASSIGN`, `AUTO_REASSIGN`. Инициалы, цвет аватара и формат показа
времени вычисляет фронтенд. Поиск, счётчики и эти DTO не требуют новых таблиц.

## 2. Ручки

### Общие правила HTTP

- JSON — `snake_case`; ID — UUID; даты — `YYYY-MM-DD`; время — ISO 8601 с зоной.
  Расстояния в метрах, длительности в секундах; минуты и формат времени для показа
  вычисляет фронт. Внутренние UI-типы могут оставаться camelCase.
- Вход — серверная сессия в HttpOnly cookie того же сайта. В production cookie
  имеет Secure и SameSite=Lax. После входа Java выдаёт `csrf_token`; фронт передаёт
  его заголовком `X-CSRF-Token` в изменяющих запросах. Java проверяет Origin при
  входе. Пользователь и роль определяются сессией, а не полями запроса.
- Симулятор входит через тот же `/auth/login` под учётной записью моделируемого
  представителя, сохраняет cookie и передаёт CSRF-токен по тому же протоколу.
  Доступ «представитель» ниже относится и к PWA, и к симулятору. Отдельного обхода
  проверок или права менять чужие заявки у симулятора нет.
- У GET нет тела. Списки принимают `page` от 1 и `page_size` от 1 до 100,
  по умолчанию 10. Ответ списка: `{items, total, page, page_size, clock}`.
  Лента представителей последовательно догружает такие страницы.
- `date` — выбранный в интерфейсе день; если не передан, Java берёт текущий
  модельный день. `search` и фильтры приходят из полей интерфейса; пустые фильтры
  не передаются. `total` считает Java по всей отфильтрованной выборке.
- Бизнес-команды ниже отправляются с `Idempotency-Key: <UUID>`. Фронт создаёт
  ключ для одного действия и сохраняет его при повторе запроса после сбоя сети.
  Java сама создаёт `request_id` для вызова расчётчика и связывает его с командой.
- Ошибка: `{error: {code, message, details}}`. HTTP: 400 — неверные данные,
  401 — нет сессии, 403 — нет прав, 404 — нет объекта, 409 — конфликт,
  422 — невыполнимое действие/план, 500 — сбой. При конфликте Java возвращает
  в `details` актуальную заявку и причину; фронт обновляет карточку.

Python-симулятор действует через те же ручки, тела, сессии и проверки, что PWA.
Это относится к расписанию, деталям заявки, статусу, задержке, обоим отказам,
позиции и sync. Внутренний Python-расчётчик вызывается Java отдельно.

Изменяющие бизнес-запросы передают `X-Scenario-ID` из последнего `clock.scenario_id`.
Это относится также к `/demo/reset`, `/demo/scenarios`, статусам, задержкам,
обоим отказам, позиции и `/sync`; вход и профиль этот заголовок не требуют.
Java отклоняет новый запрос из старого сценария как 409 `SCENARIO_RESET`.
Для уже известного `Idempotency-Key` сначала проверяется совпадение команды:
сохранённый результат может быть возвращён с его исходным `clock.scenario_id`.
Фронт не применяет ответ к другому сценарию. Журнал команд сохраняется при сбросе;
уникальность `(actor_id, idempotency_key)` действует через границы сценариев.
Успешная собственная reset-команда — ожидаемое исключение: она переводит клиента
на новое поколение, после чего выполняются свежие GET. Если повтор старой
reset-команды вернул уже устаревший результат, клиент читает текущий `/workday`
и не откатывает поколение к сохранённому ответу.
При активации плана Java повторно проверяет текущий сценарий, доступность на день
и исключения отказов: одной сверки версий заявки недостаточно.

### Вход и профиль

#### `POST /auth/login` — войти

**Описание:** проверить учётные данные и открыть серверную сессию.

**Вызов:** пользователь нажимает «Войти» на странице входа вместо выбора демороли.

**Авторизация:** не нужна.

**Тело:** `{login, password}` — введённые учётные данные.

**Ответ:** 200, `UserView`; Java устанавливает cookie сессии.
Роль приходит из учётной записи, выбрать её в запросе нельзя.

#### `GET /me` — восстановить сессию

**Описание:** получить пользователя текущей серверной сессии.

**Вызов:** запуск приложения или перезагрузка; результат заполняет верхнюю панель,
профиль и определяет доступный раздел.

**Авторизация:** любой вошедший пользователь.

**Ответ:** 200, `UserView` из сессии Java; при отсутствии сессии — 401.

#### `PATCH /me` — изменить имя

**Описание:** сохранить новое имя текущего пользователя.

**Вызов:** «Сохранить» в настройках профиля, открытых через аватар.

**Авторизация:** любой вошедший пользователь, только свой профиль.

**Тело:** `{name}` — новое имя из формы, от 2 до 64 символов.

**Ответ:** 200, обновлённый `UserView`. Java сохраняет имя учётной записи;
роль и привязка к представителю этим запросом не меняются.

#### `POST /auth/logout` — выйти

**Описание:** завершить текущую серверную сессию.

**Вызов:** «Выйти» в меню аватара.

**Авторизация:** любой вошедший пользователь.

**Тело:** нет.

**Ответ:** 204; Java завершает сессию, фронт очищает её данные и открывает вход.

### Загрузка экранов

#### `GET /workday` — сводка рабочего дня

**Описание:** общие показатели дня, независимо от открытой страницы списка.

**Вызов:** открытие панели диспетчера, возврат в приложение, завершение бизнес-команды.

**Авторизация:** диспетчер.

**Query:** `date`.

**Ответ:** 200, `WorkdayView`. Java считает показатели по заявкам, активным
назначениям, представителям и алертам выбранного дня. `has_routes` — наличие
активных маршрутов, `offices` — офисы дня.

#### `GET /orders` — список заявок

**Описание:** поиск и фильтрация заявок выбранного дня.

**Вызов:** открытие вкладки «Заявки», изменение поиска/фильтра/страницы;
также список под карточками команды после выбора представителя.

**Авторизация:** диспетчер.

**Query:** `date, search, status, courier_id, assigned, page, page_size`.
`status` фильтрует показываемый `day_status`; `assigned=false` — без подтверждённого
назначения. `courier_id` берётся из выбранной карточки представителя.

**Ответ:** 200, `Page<OrderView>`. Java включает перенесённые с выбранного
дня заявки по истории, чтобы их результат не исчезал из диспетчерского обзора.

#### `GET /orders/{id}` — полная карточка заявки

**Описание:** получить одну заявку, даже если её нет на загруженной странице списка.

**Вызов:** клик по строке заявки, «Подробнее» в popup карты, переход из истории
или открытие встречи представителем.

**Авторизация:** диспетчер; представитель — только своя заявка.

**Query:** `date` для представления результата выбранного дня.

**Ответ:** 200, `{order: OrderView, alerts: AlertView[], clock: Clock}`;
включаются только разрешённые пользователю алерты. История подгружается отдельным запросом ниже.
`id` берётся из строки, маркера или ссылки; Java собирает указанные выше DTO.

#### `GET /couriers` — представители

**Описание:** карточки команды и кандидаты для ручного назначения.

**Вызов:** открытие «Представители», изменение фильтров, прокрутка к концу ленты;
также открытие выбора получателя в карточке заявки.

**Авторизация:** диспетчер.

**Query:** `date, search, is_available, has_open_alerts, workload, page, page_size`.
`workload=assigned|unassigned` — есть ли незавершённые назначения на выбранный день.

**Ответ:** 200, `Page<CourierView>` со счётчиками. Java фильтрует всю
команду; окончательную выполнимость переназначения проверяет расчёт.

#### `GET /couriers/{id}/schedule` — расписание представителя

**Описание:** все остановки одного представителя с нужными для экрана данными.

**Вызов:** открытие «Мой день»/«Маршрут» представителем или выбор человека на карте
диспетчера; симулятор читает это же расписание перед выполнением действий.
`id` приходит из сессии или выбранной карточки.

**Авторизация:** представитель — своё расписание; диспетчер — любого представителя.

**Query:** `date`.

**Ответ:** 200, `{date: date, courier: CourierView, route: RouteView|null,
orders: OrderView[], offices: OfficeView[], clock: Clock}`; `route=null`,
если активного маршрута нет. Java объединяет активный маршрут, остановки и заявки;
прогресс и ближайшую остановку фронт показывает по этому полному расписанию.

#### `GET /workday/map` — общая карта

**Описание:** все данные карты, независимо от пагинации таблицы заявок.

**Вызов:** открытие обзора диспетчера и обновление после изменения плана/статусов.

**Авторизация:** диспетчер.

**Query:** `date`.

**Ответ:** 200, `MapView` с полями, определёнными в первой части документа.
`stops` и геометрия определены в DTO маршрута. Связи `alerts.order_ids`
используются для красных маркеров заявок.

#### `GET /alerts` — алерты диспетчера

**Описание:** сообщения, требующие решения, и уже обработанные сообщения.

**Вызов:** открытие «Алерты», поиск, фильтры или переход на другую страницу списка.

**Авторизация:** диспетчер.

**Query:** `date, search, status, severity, page, page_size`.

**Ответ:** 200, `Page<AlertView>`. Открытие строки использует
эти детали; отдельная ручка деталей пока не нужна. Индикатор меню берёт общий
`open_alerts` из сводки, а не количество записей текущей страницы.

**Описание:** аудит действий рабочего дня или конкретной заявки.

в карточке заявки после загрузки её деталей.

**Авторизация:** диспетчер.

**Query:** `date, search, type, actor_role, order_id, page, page_size`.

**Ответ:** 200, `Page<HistoryEntry>` из аудита Java. `order_id` — ID
открытой заявки; модальное окно использует детали полученного события.

### Изменение рабочего дня

#### `POST /planning-jobs` — построить маршруты

**Описание:** запустить назначение загруженных заявок и построение плана.

**Вызов:** «Построить маршруты» в панели диспетчера.

**Авторизация:** диспетчер.

**Тело:** `{date, algorithm?}`; день из интерфейса, алгоритм `greedy|ortools`,
по умолчанию `greedy`. Настройки расчёта и модельное время Java заполняет сама.

**Ответ:** 202, `{operation_id, clock}`. ID создаёт Java для отслеживания команды.

#### `GET /operations/{id}` — дождаться результата команды

**Описание:** отслеживать генерацию дня, расчёт или перераспределение.

**Вызов:** периодически после ответа 202, пока команда не завершится.

**Авторизация:** диспетчер; представитель — только свои команды.

**Ответ:** 200, `OperationView`: `{id, status, result, error, clock}`.
`status=pending|running|succeeded|failed`; результат и ошибка равны `null` до готовности.
Для расчёта результат содержит `plan_version, affected_courier_ids, metrics` из
принятого результата Python. Успех означает активацию Java, а не просто запись плана.
`error={code, message, details}`. После успеха фронт перечитывает нужные экраны.

#### `POST /orders/{id}/reassignment` — передать заявку выбранному представителю

**Описание:** ручное решение диспетчера по открытому алерту.

**Вызов:** «Назначить» после выбора представителя в карточке заявки.

**Авторизация:** диспетчер.

**Тело:** `{alert_id, target_courier_id, base_version, reason?}`: ID связанного
алерта, выбранного представителя, `order.version` из карточки и текст из формы.

**Ответ:** 202, `{operation_id, clock}`. Java проверяет алерт и версию, запускает
перерасчёт; `IN_PROGRESS`/`COMPLETED` не переназначает. Причина — `MANUAL_DISPATCHER`.
После активации нового назначения закрывается элемент `alert_order` этой заявки.
Если алерт объединяет заявки после отказа на день, он остаётся открытым, пока
не решены все его элементы; одна ручная передача не закрывает остальные.

#### `POST /alerts/{id}/auto-reassignment` — перераспределить автоматически

**Описание:** поручить системе найти решение для заявок алерта.

**Вызов:** кнопка «Перераспределить автоматически» в карточке алерта.

**Авторизация:** диспетчер.

**Тело:** нет; затронутые заявки Java берёт из ещё не решённых элементов `alert_order`.

**Ответ:** 202, `{operation_id, clock}`. По истечении 10 модельных минут Java
запускает ту же бизнес-операцию самостоятельно; открытая страница для этого не нужна.

#### `POST /orders/{id}/status` — изменить статус встречи

**Описание:** зафиксировать доступный представителю переход состояния.

**Вызов:** «Выехать», «Я прибыл», «Начать встречу», «Завершить успешно» на встрече;
другие переходы показываются только при наличии в `available_actions`.
Симулятор отправляет тот же запрос, когда моделирует соответствующее действие.

**Авторизация:** представитель — только своя заявка.

**Тело:** `{status, courier_id, occurred_at, base_version, reason?}`.
`status` — действие кнопки, `courier_id` — сессия, `base_version` — версия карточки,
`occurred_at` — модельные часы действия; `reason` — введённая причина при необходимости.

**Ответ:** 200, `{result, order, clock}`; `result=APPLIED|DUPLICATE`, заявка уже
с новой версией. Java проверяет переход и владение, конфликт возвращает как 409.

#### `POST /orders/{id}/delay` — сообщить о задержке

**Описание:** записать задержку и проверить её влияние на маршрут.

**Вызов:** «Сообщить диспетчеру» в форме задержки открытой встречи;
симулятор отправляет этот запрос при моделировании задержки.

**Авторизация:** представитель — только своя заявка.

**Тело:** `{delay_s, occurred_at, base_version}`; минуты из формы умножаются на 60,
время — модельные часы, версия — из карточки.

**Ответ:** 202, `{operation_id, clock}`. Java создаёт событие `COURIER_DELAYED`,
обновляет ETA через расчёт и создаёт алерт при проблеме с окнами. Результат операции
содержит `alert_id` либо `null`, если решения диспетчера не требуется.

#### `POST /orders/{id}/refusal` — отказаться от одной заявки

**Описание:** сообщить, что представитель не может выполнить конкретную встречу.

**Вызов:** подтверждение «Отказаться от встречи» в её карточке;
симулятор отправляет этот же запрос при моделировании отказа от заявки.

**Авторизация:** представитель — только своя заявка. После `IN_PROGRESS`
или `COMPLETED` этот отказ недоступен.

**Тело:** `{reason, occurred_at, base_version}` — причина из формы,
модельное время действия и `order.version` из карточки; `Idempotency-Key`.

**Ответ:** 200, `{order: OrderView, alert: AlertView, clock: Clock}`. Java сохраняет отказ с ID заявки,
представителя и причиной, повышает `order.version` и создаёт алерт с `order_ids=[id]`. Назначение сохраняется
до решения; действия представителя по этой встрече блокируются. Его
`is_available`, другие встречи и возможность брать другие заявки не меняются.

Диспетчер получает 10 модельных минут на выбор другого представителя или запуск
автоматического решения; затем перераспределение запускает Java. Отказавшийся
представитель исключается из кандидатов именно для этой заявки. Java хранит это
ограничение вместе с событием отказа, чтобы его учитывал и расчётчик.

Для расчётчика используется `ORDER_REFUSED`; Python читает сохранённый отказ
при любом перерасчёте, включая ручной выбор и автоматическое решение.
`COURIER_REFUSED` относится к отдельной ручке отказа на день ниже.

#### `POST /couriers/{id}/refusal` — отказаться от всех оставшихся заявок на день

**Описание:** прекратить приём новых встреч и передать оставшиеся встречи текущего
рабочего дня другим представителям. Уже начатую встречу представитель завершает сам.

**Вызов:** отдельное действие «Отказаться от всех заявок на сегодня» в интерфейсе
представителя; симулятор отправляет ровно этот же запрос при моделировании отказа на день.

**Авторизация:** представитель — только за себя; `id` связан с его сессией.

**Тело:** `{date, reason, occurred_at}` — текущий модельный день, причина отказа
и модельное время действия. Для другого дня Java возвращает 400.

**Ответ:** 200, `{courier: CourierView, alert: AlertView|null,
affected_order_ids: UUID[], clock: Clock}`.

Java одной транзакцией сохраняет `COURIER_REFUSED`, делает представителя недоступным
для новых назначений в указанном дне (`is_available=false`, `availability_date=date`)
и определяет его заявки в состояниях `ASSIGNED`, `EN_ROUTE`, `ARRIVED`.
Они входят в `affected_order_ids`; `IN_PROGRESS`, `COMPLETED`, `CANCELLED`
и уже перенесённые с этого дня заявки не затрагиваются. Для включённых заявок
Java повышает `version`, сохраняет назначение до решения и блокирует дальнейшие
действия отказавшегося представителя. Уже начатую встречу можно завершить
и сообщить о её задержке.

Для заявок, ещё не включённых в открытые алерты отказа, создаётся один новый
алерт `kind=refusal`, `scope=courier_day` с `order_ids` и элементами `alert_order`.
Ранее открытые алерты сохраняют свои ссылки и дедлайны; их заявки повторно
не включаются в новый алерт. `affected_order_ids` при этом содержит все
определённые выше оставшиеся заявки, включая уже покрытые алертами отказа.
Если все они уже покрыты, `alert=null`, но список затронутых заявок не пуст.
Если передавать нечего, `alert=null`, `affected_order_ids=[]`; новые назначения
на день всё равно запрещены. Повторный отказ не создаёт дубликаты алертов.

Диспетчер может передавать заявки по одной или запустить автоматическое решение
для оставшихся элементов алерта. Java запускает автоматическое решение по его
десятиминутному дедлайну. Решение по одной заявке не закрывает остальные элементы
и не меняет дедлайн алерта. Python исключает отказавшегося представителя
из назначений на этот день. На следующий день ограничение отказа на день
не переносится автоматически; Java формирует доступность для новой даты.

#### `POST /demo/scenarios` — загрузить синтетический день

**Описание:** получить новый сценарий от генератора и сохранить его через Java.

**Вызов:** «Загрузить заявки» диспетчера, когда учебный день пуст.

**Авторизация:** диспетчер; ручка включена в учебном окружении.

**Тело:** `{date, seed?}` — выбранный день и необязательный seed для повторения

**Ответ:** 202, `{operation_id, clock}`; результат операции содержит фактический
`seed, orders_count, couriers_count`. Затем фронт загружает сводку и списки.

#### `POST /demo/reset` — очистить учебный сценарий

**Описание:** очистить данные сценария, включая ожидающие операции старого дня.

**Вызов:** «Очистить день» в панели диспетчера.

**Авторизация:** диспетчер; только учебное окружение.

**Тело:** нет.

**Ответ:** 202, `{operation_id, clock}`. Java инвалидирует старые команды;
после завершения фронт перечитывает пустую сводку и очищает выбранные объекты.

### Для этапа геолокации и PWA

#### `POST /couriers/{id}/position` — передать последнюю позицию

**Описание:** дать серверу координаты представителя с временем измерения.

**Вызов:** во время активной работы приложения после разрешения геолокации;
симулятор отправляет сюда смоделированную позицию. Текущий UI её ещё не отправляет.

**Авторизация:** представитель — только за себя.

**Тело:** `{lat, lon, at}` — браузерная геолокация и модельное время измерения.

**Ответ:** 204. Java обновляет `courier.position`; симулятор использует ту же операцию.

#### `POST /sync` — отправить накопленные действия

**Описание:** передать статусы, сохранённые будущей PWA без связи.

**Вызов:** восстановление соединения или повтор отправки из приложения.
Симулятор использует ту же пачку для моделирования восстановления связи.

**Авторизация:** представитель — свои действия.

**Тело:** `{actions: SyncAction[]}`; поля действий определены в первой части.
ID создаёт outbox фронта; остальные значения сохраняются в момент действия,
не заменяются временем отправки. Java применяет правила конфликтов и дубликатов.
`client_action_id` совпадает с `Idempotency-Key` прямой отправки того же действия,
если клиент повторяет его через sync после потерянного ответа.

**Ответ:** 200, `SyncResult`; для каждого ID — `APPLIED`, `DUPLICATE` либо
`CONFLICT` с причиной и доступной актуальной заявкой. IndexedDB/outbox пока не реализованы.
Этот формат пачки содержит только статусы. Задержка и оба отказа пока
отправляются отдельными командами онлайн.

После команд и при возвращении на экран повторяем нужные GET; для новых алертов
и изменения часов начинаем с периодического опроса. SSE/WebSocket сейчас не нужны.
Расчётные Python `/assign`, `/reassign` и callback `/plans/ready` — внутреннее
взаимодействие сервисов. Управление часами и подготовка сценария относятся
к служебному контуру симуляции; альтернативных ручек для действий представителя
в `/sim/*` не создаём. Симулятор и PWA проходят один путь обработки в Java.
