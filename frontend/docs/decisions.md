# RouteRoad — принятые решения

Актуализировано 08.11.2026. Этот файл описывает выбранное направление проекта;
готовые функции отделены от плана интеграции.

## 1. Продукт и роли

Учебная диспетчеризация доставки банковских карт в Новосибирске. Данные полностью
синтетические. Представитель передвигается на автомобиле, работает по всему городу
и привязан к офису, где получает карты.

Один React/TypeScript frontend содержит интерфейс диспетчера и представителя.
Диспетчер управляет днём, заявками, маршрутами и алертами; представитель видит
свои встречи и выполняет разрешённые действия. Java проверяет права каждой
операции. Выбор демороли в браузере не является авторизацией.

## 2. Данные и границы сервисов

[entity.md](entity.md) — внутренний контракт Java/Python. Java владеет основными
данными, миграциями PostgreSQL/PostGIS, временем, конфликтами и активацией планов;
Python считает и записывает таблицы плана. Kafka и Redis для текущего этапа
не требуются. Браузер обращается к Java через REST/JSON, не к Python или БД.

PWA получает данные этих же общих таблиц через Java. Python-симулятор вызывает
ровно те же Java-ручки статусов, задержки, отказа, расписания, позиции и sync,
что PWA, с теми же телами и проверками. Расчётчик Python — другая роль;
его `/assign` и `/reassign` остаются внутренними вызовами Java.

Фронтенд не повторяет серверные таблицы. В [frontend-api.md](frontend-api.md)
определяем необходимые UI запросы и ответы. Java объединяет данные и вычисляет
агрегаты; дополнительные адрес, продукт, номер, алерты и аудит входят в требования
Java API, даже если их нет во внутреннем контракте расчётов. Их источники указаны
рядом с полями. Все обновлённые сущности, расширения схемы, DTO и ручки собраны
в этом одном файле: это результат задачи для Java-разработчика.

Профиль, алерт, краткая заявка и сводка дня могут быть отдельными DTO без отдельных
таблиц в браузере. Store хранит состояние экранов, API-адаптер переводит формат
и проверяет данные. Инициалы/оформление вычисляются на фронте; бизнес-факты
из координат или случайных строк не восстанавливаются.

## 3. Рабочий процесс интегрированного UI

Java загружает и сохраняет синтетический сценарий по команде диспетчера.
Построение маршрутов — отдельная команда. Длительная операция возвращает ID,
frontend опрашивает её состояние; готовность плана наступает после проверки
и активации Java. Python callback и внутренние request_id не управляются React.

Списки запрашиваются постранично с поиском и фильтрами на Java. Размер по умолчанию
10, без настройки в UI; лента представителей догружает следующие порции.
Детали заявки, сводка и карта загружаются отдельно. Общие счётчики относятся
ко всему дню, а не к странице списка.

Маршрут содержит упорядоченные остановки и ETA, включая повторные заезды в офис.
После частичного пересчёта у активных маршрутов могут быть разные plan_version.
Дорожная геометрия приходит через Java; браузер не рассчитывает оптимизацию.

## 4. Алерты и действия представителя

Окно заявки задаёт время начала встречи, длительность показывается отдельно.
Java возвращает допустимые действия; frontend отображает их, а сервер повторно
проверяет команду. Начатую или завершённую встречу нельзя передать другому.

Поддерживаются два отказа: от одной заявки и от всех оставшихся встреч на день.
Первый сохраняет доступность представителя для остальных заявок; второй
запрещает новые назначения на этот день. Начатую встречу представитель может
завершить. Поля, правила и обе ручки полностью описаны в `frontend-api.md`;
симулятор использует эти же операции.

При необходимости перераспределения Java создаёт алерт. Диспетчер может выбрать
представителя или запустить автоматическое решение; через десять модельных минут
без решения действует Java. До решения назначение сохраняется. Это выбранная
последовательность для фронтового сценария, внутренние вызовы координирует Java.

Таймер использует модельное время и скорость из API. Истечение срока в браузере
ничего не назначает. Доступность представителя, нахождение на смене и наличие
алертов — разные признаки.

Перенос отображается как `day_status=RESCHEDULED` в выбранном дне, с новой датой.
Внутренний `service_order.status` может уже быть `NEW` на следующий день;
Java строит представление дня по аудиту. Изменение внутреннего контракта не нужно.

## 5. Сессия и будущий PWA

Для браузера выбираем same-origin HttpOnly cookie-сессию и CSRF-защиту мутаций.
Роль и связь с представителем определяет Java. Регистрацию/выдачу ролей через UI
в текущую задачу не включаем.

Будущий PWA хранит ранее полученное расписание/маршруты и outbox в IndexedDB.
Локальное действие отдельно от серверного результата; оно имеет постоянный ID,
исходную версию и время. Java возвращает по каждому действию APPLIED, DUPLICATE
или CONFLICT с актуальными данными. Frontend показывает результат и не применяет
собственную стратегию перезаписи серверного состояния.

Не обещаем офлайн-карту и фоновую отправку из закрытого браузера. Наличие manifest,
service worker или Zustand persist само по себе не доказывает офлайн-поддержку.

## 6. Что реализовано сейчас

React/TypeScript, Vite, Tailwind и отдельные Zustand-stores дня, демосессии и UI.
Layer/type-based структура: pages/components/stores/hooks/api/types/utils/routes.
Все файлы и компоненты страниц заканчиваются на Page; Atomic Design — принцип
композиции без обязательных atoms/molecules/organisms.

Асинхронный demo API работает в памяти: старт пустой, загрузка заявок отдельно
от предопределённых маршрутов, ошибки/повтор, поиск и фильтры, карточки и аудит.
День очищается при перезагрузке; демороль и имя профиля — в sessionStorage.
Текущие демодействия проще выбранного серверного сценария; HTTP-клиента пока нет.

Desktop-sidebar сворачивается кнопкой на панели; бургер только на мобильном.
Аватар открывает профиль, алерты обозначаются индикаторами. Интерфейс представителя
использует ширину планшета; «Мой день» показывает прогресс и ближайшую встречу,
«Маршрут» — карту и остановки. Панели карты скрываются через контекстное меню.

Leaflet отображает онлайн-тайлы OSM с атрибуцией; демолинии прямые, без оптимизации.
UI-иконки — SVG-компоненты Lucide. Единственный авторский CSS — global.css.
Code Inspector включён только для локального Vite, Ctrl+Alt+клик.

Общий Compose в корне RouteRoad содержит production frontend. Dockerfile собирает
dist и передаёт его Nginx; dev-контейнера нет, разработка идёт через локальный Vite.
До интеграции Nginx отвечает JSON 503 на `/api`.

Проверки — TypeScript, ESLint, Prettier и build. E2E-набор и Playwright удалены
по просьбе пользователя; e2e/ оставлена. Изменения UI проверяются вручную.
Настоящая авторизация, Java API, расчёт, PWA и синхронизация ещё не подключены.

## 7. Проверка архитектуры — 09.11.2026

Сохраняем layer/type-based структуру. Общие PageHeader и EmptyState находятся
в ui; обратная связь рабочего дня — отдельный контейнер. Сводка и drawer получают
готовые props. Детали заявки читаются по ID через API, включая переход из истории
или карты; выбор представителя не зависит от наличия его ID в общем снимке.
Интерфейс источника вынесен в types, фабрика store получает источник и провайдер
контекста отдельно. Зависимости UI/данных дополнительно ограничены ESLint.

Для проверки без Java остаётся demo API с DEV-задержкой и первой ошибкой
выбранных чтений/изменений. Реальные HTTP-ответы ещё не подключены: перед этим
понадобятся DTO-адаптеры, отдельные чтения, async-команды и сессия. Подробный порядок
и ограничения зафиксированы в frontend-architecture.md; серверный контракт
frontend-api.md при этом не меняется. MSW можно подключить на этапе первого
HTTP-клиента, сейчас дополнительная зависимость не нужна.
